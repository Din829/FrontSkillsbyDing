## 三层检查（判断框架，不是填表）

每层回答相关项目的核心问题。**不是固定问题列表**，按项目特点取用。

- **结构层**：核心信念是否被遵守？接口契约是否被绕过？架构分层是否被打破？
- **承诺层**：PROGRESS / 文档每条"已完成"对应代码真存在吗？测试是 shape 还是 behavior？
- **一致性层**：文档与代码一致？不同文档之间术语统一？装配示例真能跑？

## 典型可疑信号（grep 时找什么）

按项目特点取用，不必每项都跑。

**核心层不该有的东西**
- 具体厂商 SDK import（`from 'openai'` / `from 'anthropic'`...）
- 数据库驱动 / HTTP 框架 / 文件系统操作（在协议层是异常，在 loader 是允许边界）

**接口被绕过的迹象**
- 适配器调用别的适配器（横向依赖）
- 业务工具直连具体后端、跳过接口
- 装配代码内嵌业务逻辑

**承诺未兑现的迹象**
- 测试名含 "shape" / "structure" / "type" 多半在测 shape
- 文档说"自动覆盖 X"——找 X 实际生效路径，验证默认装配下生效
- PROGRESS 自报"已修"但 grep 不到对应代码改动
- mock 重的测试——mock 掉的恰好是承诺的关键行为，等于没测
- 靠单次运行下的结论——有抖动的（网络 / 并发 / 时序）单次孤证不算数

**文档不一致的迹象**
- 装配示例 import 的 export 在源码不存在
- 流程图步骤实际代码没对应
- 同一概念在不同文档用不同名字

**事实没核的迹象**
- 注释引用"contract test in xxx"——验证真有这个测试
- 注释说"Stage N will add X"——已过 Stage N 还在说就是陈旧
- 文档说"SDK 默认是 X"——亲打开 SDK 源码核

**过度防御的迹象**（判断词：这层防御在系统边界吗？）
- 包了又包的 try/except——内层吞掉异常，外层永远收不到，根因找不出
- 可选字段配 fallback 默认值——掩盖配置错误，fail silent
- hardcode 截断（max_pages / max_rows 之类）——闷头丢数据伪装成成本防御
- 内部可信调用做边界校验——相信类型和契约，fail loud 比 fail safe 有价值
- 注意：在真正的系统边界（用户输入 / 外部 API / 文件 IO / 数据库读出）防御是**对的**，别反向一刀切

**灵活性失衡的迹象**（判断词：这个值会变吗？变了要改几处？）
- `if "关键词" in query` 式的业务分支——关键词必然演化
- 写死的 URL / 端点 / 模型名——环境一换就断
- 业务策略性的魔法数字——阈值散落多处，改一个漏一个
- 注意：不会变的（格式语法、标准事实）或只影响一处的启发式系数，硬编码**合理**，别强行配置化

**过度复杂的迹象**（判断标准：必要复杂度，不是行数）
- 只有一个实现的接口层 / 抽象层——等真有第二个实现再抽
- 没人消费的配置项、没人 import 的导出
- 只透传的包装层——删掉直连，行为不变
- 自问：高级工程师看了会不会觉得过度设计？会就是信号
