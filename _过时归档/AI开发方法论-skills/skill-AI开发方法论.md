# AI 开发方法论 skill

> 本 skill 教 CodingAgent 在**非平凡项目**里有节奏、不跑偏地推进。
> 兄弟文件（同目录下）：`模板-项目定位.md` / `模板-PROGRESS.md` / `清单-审查checklist.md`。本 skill 让 agent 在合适阶段把这些复制到项目里使用。

## 何时触发本 skill

**用户显式说"按 AI 开发方法论 skill 推进"** 时启用。

适用：多文件、多模块、多阶段、长周期项目。
不适用：一两百行的脚本、临时调试、一次性数据处理。简单任务用这套流程是过度设计。

---

## 心法（贯穿全程的几条铁律）

这 5 条是后面所有阶段动作的根。每条都是实战踩出来的，不是装饰。

### 1. 核心信念是锚，不是序言

项目定位文档里的"核心信念"必须**真的被反复引用**——做架构决策、写实现、跑审查时，先把信念条目拉出来比对，再决定怎么做。

不是写完就忘的"项目愿景"。每个 PR / 修复 / 审查都要显式问"对照信念哪几条"。

### 2. 承诺 = 行为，不是 shape

文档说"做了 X"——必须有**真行为测试**兜底，而不是"返回值字段长这样"的 shape 测试。

反例：buildAgent 返回 `runConfig: { traceIncludeSensitiveData: false }`，测试断言这个字段是 false——但 SDK 实际从 `Runner.config` 读这个字段、不是从 per-run options 读。结果"测试全过 + 文档承诺合规"实际没生效。

每次写完测试问自己：**测的是 shape 还是 behavior？这个返回值真的会被消费吗？消费后会不会被覆盖?**

### 3. 事实 ≠ 结论

SDK / 库 / API 的具体行为——**亲自核源码或官方文档**，不凭印象。

特别是：版本相关行为、默认值、已知 bug、类型签名。

CLAUDE.md 里写过这条；本 skill 再次强调因为这是 AI 最容易绕过的——会习惯性给一个看着合理的答案。**当你打算写"SDK 的 X 是 Y"，先问一句"这是事实还是我的印象？"**。

### 4. 给方案要拍板，不要罗列

向人确认时给方案 A/B（最多 C），**明确推荐**哪个 + 一句话 trade-off + 为什么更符合核心信念。

人不懂技术细节，agent 比人懂。让人看一眼 "我推荐 A，因为..." 就能拍板，比"以下 5 种方案各有优缺点请选"友好得多。

但**不是 agent 单独决策**——拍板权在人，只是 agent 不能把"罗列让人选"当中立。

### 5. 良好检查习惯：靠习惯不靠记性

agent 注意力会随上下文累积衰减——**靠机械动作维持精度，不靠"我应该记得"**。

- **动手前先读相关文件**：不是全读，是 grep / Glob 锚定相关部分，再 Read 那一段。减少幻觉、增加对修改的把握。
- **改后回看 diff**：可疑的改动问自己"这是用户要的吗"。顺手的风格调整、无关重构通常该 revert；笔误或 bug 修复保留但要说明。
- **检查靠 grep + 稳定 heading，不靠记性**：PROGRESS / 项目定位用稳定的标题模板写就是为这个。审查时 grep `## Step` / `### 信念检查` 精确跳到要看的部分，不用通读。
- **多文件多模块改动后，跑全套 typecheck + test**：改了一处可能动了别处。纯注释 / 文案 / 独立新增不必——判断词：**改动会不会让别人读到的东西变了？**没变就别上仪式。
- **同类核对超过 2 次就停下来汇报**：不要用重试代替思考。

这条贯穿全程：设计期读 SDK 类型签名要先 grep 定位、开发期改完一定看 diff、审查期靠 grep 不靠记性。

## 阶段一：启动 —— 写"项目定位"

### 做什么

复制本 skill 兄弟文件 `模板-项目定位.md` 到**项目根目录**，命名 `项目定位.md`，按模板填。

### 项目定位的角色

agent 时刻回顾的"身份卡"。后面所有阶段的决策都要回到这张卡。

必须**短**（一两屏内能读完，<200 行），必须**显眼**（项目根目录顶层），必须**可被 grep**（核心信念条目用稳定短语写，方便后续审查时一字不差引用）。

### 内容关键

- 做什么 / 不是什么 / 面向谁 —— 划清边界比说做什么更重要
- 核心信念 3-6 条短句 —— 每条用稳定短语，不要写散文
- 类比 / 对标（可选）—— 跟谁同思路、跟谁不同

### 反模式

- ❌ 核心信念写成抽象大词（"高质量"、"可扩展"、"用户友好"）—— 等于没写
- ❌ 信念写成长段落 —— grep 不到，agent 后续没法引用
- ❌ 把需求文档当项目定位 —— 项目定位是身份不是清单
- ❌ 写完不看 —— 起草后跟用户确认每一条信念是不是真的"贯穿全文档的铁律"，不是"听着像那么回事"

### 与人协作

向用户确认**意图和边界**，不确认实现细节：
- "做框架还是产品？" ← 确认
- "面向 toB 还是 toC？" ← 确认
- "用 React 还是 Vue？" ← 不必（人不懂 / 不重要 / agent 懂）

### Terminal state

阶段一**唯一的下一步**是用户拍板项目定位、显式说"进设计阶段"。**不要自己跳到写代码 / 起草设计文档**。

---

## 阶段二：设计 —— 起草设计文档

### 做什么

根据项目复杂度判断：
- **简单**：一份合并文档（既讲架构又列计划）
- **中等**：拆 ARCHITECTURE + DEVELOPMENT_PLAN 两份
- **复杂**：再加 REQUIREMENTS / API 等专项

**不强制三件套**。看哪个能让 agent 注意力集中、不冗长。

### 关键约束

- 文档为 agent 注意力服务，不为完备性服务 —— 长文档 = 注意力分散
- 每个外部依赖必须列出"通过哪个接口接入" —— 这是"加能力不动 core"的落实
- 装配示例代码必须能跑，不能只是 pseudo-code —— 否则文档与代码漂移
- 跨文档术语统一 —— 同一概念在 A 文档叫 X、B 文档叫 Y 是病

### 给方案要拍板

设计期最容易卡在"几条路线选哪条"。规则：
- 给 1-3 个方案，**明确推荐一个**
- trade-off 一句话
- 用核心信念条目说为什么推荐 A 而不是 B

人拍板后**确实推进**，不要中间又自己改主意——除非发现新事实。

### 反模式

- ❌ 文档写得像企业 RFC，几千行 —— agent 读不完
- ❌ 为不存在的客户场景设计 —— 等真有需求再加
- ❌ 把 SDK / 库已有抽象重新发明一遍 —— 直接复用 SDK 的 `tool()` / `Session` / 错误体系比包一层强
- ❌ 装配示例代码只写一半（`...`、`/* TODO */`）—— 客户照抄会断
- ❌ 过度向人确认（"用 RxJS 还是 zustand"）—— 这种问题 agent 自己拍板就行

### Terminal state

阶段二**唯一的下一步**是用户拍板设计方向、显式说"开始开发"。**不要自己跳过去写实现代码**。

## 阶段三：开发 —— 有节奏地推进

### 做什么

复制 `模板-PROGRESS.md` 到项目根目录，命名 `PROGRESS.md`。每完成一步必填一段。

单个 Step 的目标可机械验证且预计多轮迭代时（修测试 / 类型清零 / 批量迁移），可按 `skill-目标循环` 进冲刺模式：账本独立记在 `LOOP.md`，完成后摘要回写 PROGRESS 对应 Step。

### PROGRESS 的角色

- 给人看：知道进度
- 给 agent 看：下次对话能快速对齐
- 给审查 skill 看：审查时按 PROGRESS 列出的承诺逐条核

### 格式机械、内容自由

heading 模板**固定**（保证后续 grep 精确）：
```
## Step N：标题（YYYY-MM-DD）
### 做了什么
### 信念检查
### 承诺审计
### 事实核查
### 范围检查
```

每段**内容自由发挥**——不要让 agent 写废话凑字数。某项不适用直接写 `N/A —— 因为...`，但 heading 必须保留。

### 4 项自检的真实意义

- **信念检查**：这步符合 / 边界 / 违反核心信念哪几条？违反必须显式说为什么、用户是否同意
- **承诺审计**：这步兑现了文档承诺什么？测试是 shape 还是 behavior？mock 有没有掩盖真实行为？单次孤证下的结论算不算数？—— 防止"测试过 + 实际没生效"
- **事实核查**：用到的 SDK / 库 / API 行为，是亲自核过还是凭印象？—— 凭印象的必须升级为亲查
- **范围检查**：有没有顺手做的额外改动？—— 不在计划内的扩展要么 revert 要么单独说

### 诚实记账

- 未完成不能标完成
- 走偏了的写"偏差段"——比如"原计划 X，实际做的 Y，因为..."
- 测试加了多少、过了多少，每步都报数

### 反模式

- ❌ 测试只测 shape（"这个字段是 false"）不测 behavior（"runtime 真看到 false 吗"）
- ❌ AI 凭记忆说"SDK 的 X 是 Y" —— 必须打开源码或官方文档核
- ❌ 顺手做了计划外的"小改"—— 改完看 diff，可疑改动问自己"这是计划要的吗"
- ❌ PROGRESS 自报"完成"实际半成品 —— 用户拍板继续前 agent 必须显式确认这步是真完了
- ❌ 一次想推太多步 —— 一步一记账，不要"等都干完一起写"

### Terminal state

阶段三是循环的：每完成一步就回到自检 → 写 PROGRESS → 推下一步。

**主动建议进阶段四**的软触发（agent 在合适节点提一句即可，不强制中断用户节奏）：
- 完成里程碑节点（alpha / beta / 1.0 等）
- 改动了核心层 / 改动了 5+ 个文件 / 累积 5+ 个 Step
- 跨多个模块改动后

## 阶段四：审查 —— 周期性核完整性

### 做什么

里程碑结束 / 验收前 / 用户对完整性有疑虑时——复制 `清单-审查checklist.md` 到 `审查报告.md`，按清单跑审查。

### 心态

不是"鸡蛋里挑骨头",是"系统性核完整性"。

目的不是找问题数量,是确认承诺与行为对齐、信念真贯彻、文档与代码一致。

### 节奏

- **分组分批**——按依赖顺序 / 风险高低 / 模块独立性切。比如核心层先审、适配器后审。
- **每批停下汇报**——别一口气全审完出大报告。中间停下来让用户拍板、自己也清空一次工作记忆。
- **全扫完再修**——不要边发现边修。trivial（typo / import 顺序 / 死代码）例外可以顺手。
- **修复方案给推荐 + trade-off**——参考心法第 4 条。

### 三层检查（保持灵活,不机械填表）

- **结构层**：核心信念是否被遵守？接口契约是否被绕过？架构分层是否被打破？
- **承诺层**：PROGRESS / 文档每条"已完成"对应代码真存在?测试是 shape 还是 behavior?
- **一致性层**:文档与代码一致?不同文档之间术语统一?

每发现按严重度分:
- 🔴 违反核心信念 / 承诺未兑现 / 文档自相矛盾导致客户踩坑
- 🟡 行为偏离设计意图但可绕过 / 文档措辞不准
- 🟢 触发条件窄 / 设计选择 / 死代码 —— 存档不修

### 反模式

- ❌ 边走边改 —— 修了一个发现牵动十个,上下文乱
- ❌ 一口气审完再汇报 —— 后期注意力衰减、容易漏
- ❌ 审查时凭印象说"SDK 的 X 应该是 Y" —— 心法第 3 条照搬
- ❌ 修完忘了跑测试和 typecheck —— 改了一处可能动了别处
- ❌ 把不严重的存档项全列出来当"问题"显摆 —— 用户会被淹没,真严重的反而被忽略

### Terminal state

审查的下一步看结果：
- 全部 ✅ 或只有 🟢：可以验收 / 推下一里程碑
- 有 🔴 / 🟡：先全扫完出报告 → 用户拍板修法 → 修复 → 跑全套终验 → 更新 PROGRESS
- **不要边修边发布、不要修完不复测**

## 跨阶段约定

- skill 之间引用用 anchor 名字("详见 `清单-审查checklist`"),不写文件路径——这些 skill 文件可能被复制到别处,路径会变
- 主 skill 不需要每次对话都全文加载,**用户某阶段触发时读相关章节**
- 这套方法论可以演进——用的过程中遇到新反模式,在末尾"反模式合集"里加一条

## 按需查阅（开发期最常用）

agent 启动时读一次本 skill 建立认知；之后开发期**不要重读全文**，按场景 grep 对应 heading（每次只读 30-50 行）：

| 场景 | 去哪看 |
|---|---|
| 写新 Step 字段格式不确定 | 项目里 `PROGRESS.md` 上一段（活样例）/ `模板-PROGRESS.md` 骨架 |
| 写新 Step 自检卡住 | 主 skill `### 4 项自检的真实意义` |
| 信念怎么用、有哪几条 | 项目根 `项目定位.md` 第四节（grep 信念条目） |
| 心里冒出可疑想法 | 主 skill `## Red Flags` |
| 阶段切换不确定能不能进 | 主 skill `## 阶段切换 gate` |
| 审查要找什么可疑信号 | `清单-审查checklist.md` 末尾"典型可疑信号" |
| 想确认是不是反模式 | 主 skill `## 反模式合集` |
| 某个 Step 想进"改→验证→再改"的冲刺循环 | `skill-目标循环`（启动协议 + 刹车规则） |

**核心心智**：项目里的产物（`项目定位.md` / `PROGRESS.md`）是**开发期的活文档**——日常动作大部分在产物里就能解决；只有遇到字段含义、信念解释、自检判断等抽象问题才查主 skill。

## 阶段切换 gate（不可绕过）

每个 gate 是从一个阶段进下一个的**硬条件**。用 checklist 形式列，agent 进入时必须挨条核对——任一不满足就停下来汇报、不继续。

### 进阶段二（设计）前

<阶段 gate>
- [ ] `项目定位.md` 已存在于项目根
- [ ] 用户显式确认项目定位 OK（不是 agent 自己说"我觉得 OK 了"）
- [ ] 核心信念条目用稳定短语写、可被 grep
</阶段 gate>

### 进阶段三（开发）前

<阶段 gate>
- [ ] 设计文档（任意形式，简单一份 / 中等两份 / 复杂多份）已起草
- [ ] 用户拍板设计方向、显式说"开始开发"
- [ ] 复制 `模板-PROGRESS.md` 到项目根、命名 `PROGRESS.md`
- [ ] 重读项目定位核心信念，准备开发期每步对照
</阶段 gate>

### 阶段三推进中触发审查的硬条件

<阶段 gate>
**硬触发**（必须停下、建议跑审查）：
- [ ] 用户对完整性 / 承诺兑现度有疑虑
- [ ] 验收前 / 发布前
- [ ] 完成里程碑节点（alpha / beta / 1.0 等）

**软触发**（建议提一句不强制）：
- 改动了核心层 / 累积 5+ 个 Step / 跨多个模块改动
</阶段 gate>

### 进阶段四（审查）前

<阶段 gate>
- [ ] 复制 `清单-审查checklist.md` 到项目、命名 `审查报告.md`
- [ ] 列出审查范围、按依赖顺序分组、估算每批多少文件
- [ ] 重读项目定位（信念条目是核对锚）
- [ ] 重读 PROGRESS（自报承诺有哪些）
</阶段 gate>

### 审查后修复完成的退出条件

<阶段 gate>
- [ ] 全工作区 typecheck 干净
- [ ] 全套 test 全过、数字对得上 PROGRESS 测试统计
- [ ] 文档与代码一致（spot-check 几个装配示例真能跑）
- [ ] PROGRESS 已更新偏差段或新 Step
</阶段 gate>

## Red Flags（自检短表）

agent 心里冒出下面任何一条想法时——**停**。这是合理化、不是判断。

| 你心里想 | 真实情况 |
|---|---|
| "这改动太小不用记 PROGRESS" | 简单的也要记，跳过会断 grep 链 |
| "我记得 SDK 的 X 是 Y" | 凭印象不算事实，立刻去核源码或文档 |
| "这只是个 typo 不用走流程" | typo 顺手改但仍要 diff 回看 |
| "用户说按你推荐"——我得给方案 A/B 让用户选 | 用户说推荐就直接执行之前推荐的、不要又重新罗列 |
| "测试都过了应该没问题" | 测试可能只测 shape——问自己 runtime 真生效吗 |
| "顺手把这个无关的也改了吧" | diff 里看到可疑改动 → revert |
| "这步太简单不用自检 4 项" | heading 必须保留，不适用写 N/A，不要省略 |
| "大概是这样吧" | 任何"大概"都升级为亲查文档 / 源码 |
| "等都干完一起记 PROGRESS" | 一步一记账，批量记账漏检风险高 |
| "我审查过了应该都对" | 有🔴/🟡必须停下来汇报，不要自己决定怎么修 |
| "用户没问就不用主动汇报" | 阶段 gate 触发时主动停下来确认，不要闷头跑 |

**红旗的本质**：上下文累积时 agent 会找捷径——这张表是机械的、便于扫读的反捷径锚。

## 反模式合集(常踩的坑,统一参考)

把方法论 + 实战遇到的 AI 容易犯的错集中列在这。各阶段如有引用直接锚到这。

### 关于核心信念
- 信念写得太抽象 —— 用稳定短语,要 grep 得到
- 信念写完不看 —— 决策时不引用等于没写
- 把"用户友好"、"高质量"当信念 —— 不可执行,等于无

### 关于承诺
- 测试只测 shape (返回值字段对) 不测 behavior (runtime 真生效)
- PROGRESS 自报"完成"但承诺实际没兑现
- 文档说"自动覆盖 SDK 默认"——但客户照搬装配示例时根本没生效

### 关于事实核查
- AI 凭记忆给 SDK 行为答案("我记得 X 是 add 不是 replace") —— 必须亲查
- 引用了不存在的测试("contract test in xxx.test.ts pins this") —— 提到外部依赖必须验证存在
- 注释陈旧("Stage 2 will add Y") —— v1.0 之后注释应该跟进

### 关于检查习惯
- 改之前没读相关文件 —— 凭印象就动手,容易幻觉
- 改完不看 diff —— 顺手的无关改动也合并进去,污染本次提交
- 靠记性不靠 grep —— 漏检了某个测试 / 模块 / 文档,审查后才被人发现
- 多文件改动后没跑全套 typecheck + test —— 改了 A 处动了 B 处不知道

### 关于范围控制
- 顺手做计划外的改动 —— diff 里看到可疑的就 revert
- 给客户场景"留扩展位" —— 等真有需求再加
- 重新发明 SDK / 库已有抽象 —— 直接复用,薄包装

### 关于防御与复杂度
- 给"不可能发生的场景"加防御层 —— 只在系统边界防御,内部相信契约,fail loud 比 fail safe 有价值
- 业务策略写死成关键词分支 / 魔法数字 —— 判断词:会变吗、变了改几处;不会变的硬编码合理
- 包了又包、单一实现的抽象层 —— 判断标准是必要复杂度;具体可疑信号见 `清单-审查checklist` 末尾三组

### 关于和人协作
- 过度向人确认技术细节 —— 人不懂、agent 懂的事自己拍板
- 给方案罗列不拍板 —— 必须明确推荐哪个 + 为什么
- 修了发现路线选错就闷头改 —— 应该先停下汇报,确认新路线再走
- 用户说"按你推荐的来" —— 不要又开始罗列,直接按之前推荐的执行

### 关于审查
- 边走边改,边改边发现新问题 —— 上下文乱
- 一口气审完不汇报 —— 后期注意力衰减
- 把存档项当严重问题显摆 —— 真问题被淹没
- 审查后忘了跑全套 typecheck + test 终验

### 关于装配 / 模板
- 装配示例代码用 pseudo-code (`/* ... */`) —— 客户照抄会断
- 模板用 `z.enum([固定值])` 把本应开放的字段焊死 —— 接口设计意图与工具实现不一致
- 死代码留在产物里 (`PACKAGE_VERSION = '1.0.0'` 没人 import) —— 发现就清

## 触发本 skill 时,agent 应该做的第一件事

**先判断属于哪种情况**：

### 情况 A：首次进入项目（新项目启动 / 第一次显式触发本 skill）

1. 完整读一次本 skill 建立认知
2. 项目根没有 `项目定位.md` —— 进阶段一（写项目定位）
3. 项目根有 `项目定位.md` 但没 `PROGRESS.md` —— 进阶段二（设计）
4. 都有 —— 看 `PROGRESS.md` 最后一段判断当前在哪一步

### 情况 B：开发期内的新对话 / 重进项目（最常见）

**不重读主 skill 全文**。直接：

1. 读项目根 `项目定位.md`（重温信念，30 秒）
2. 读 `PROGRESS.md` 最后一两段（知道当前进度）
3. 按需查主 skill —— 遇到具体疑问时 grep `## 按需查阅` 表里对应 heading

### 全程默念

心法 5 条 + Red Flags 表是 always-on 的——不需要每次重读，但行为要符合。每个 PR / 修复 / 审查都拉出信念条目对照。
