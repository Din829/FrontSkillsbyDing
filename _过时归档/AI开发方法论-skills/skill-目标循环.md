# 目标循环 skill

> 本 skill 教 CodingAgent 对**单个可机械验证的目标**进行"改一点 → 跑验证 → 看结果"的冲刺循环，直到全绿才许停。
> 兄弟文件（同目录下）：`模板-LOOP.md`（运行时账本骨架，agent 自动复制填写，人不需要碰）。
> 可独立使用，也可作为 `skill-AI开发方法论` 阶段三中单个 Step 的冲刺模式。

## 何时触发本 skill

**用户显式说"按目标循环推进 / 进 loop 死磕这个"** 时启用；或方法论阶段三中某个 Step 满足适用条件、agent 主动建议（提一句即可，人拍板）。

适用：目标能用命令机械判定成败的任务——修失败测试、类型错误清零、lint 清零、批量迁移、覆盖率达标、让某个验收脚本通过。
不适用：设计、分析、调研、重构方向选择等无法机械判定"完成"的任务。**硬上 loop 是滥用**——循环的质量完全取决于裁判的质量，裁判是糊的，循环只会高效地走错路。

---

## 心法（贯穿全程）

### 1. 验证器就是天花板

loop 不可能比它的验证命令更聪明。验证弱（弱断言、覆盖不到关键路径），loop 会高效地收敛到一个**错误但全绿**的答案，且比人肉迭代更自信。所以 gate 检查验证命令质量不是仪式，是命门。

### 2. 输出原文是事实，"通过了"是结论

每轮验证结果必须**贴命令真实输出**进账本，不许用"测试过了"四个字代替。PASS 是事实，功能对是结论，中间差一层验证——原文在账本里，人和下一个 agent 都能复核；总结在账本里，谁也复核不了。

### 3. 重试不能代替思考

连续撞同一堵墙就停。错误指纹连续 2 轮相同 = 当前思路有问题，继续重试是用算力代替思考。停下来汇报，让人拍板换路。

### 4. 变绿的方式比变绿本身重要

loop 里 agent 最危险的捷径全是"让验证闭嘴"而不是"让代码正确"：改断言、删测试、加 skip、吞异常、给 fallback 值。这些动作让账面全绿、问题进暗处。Red Flags 表对此零容忍。

## 启动协议（对话式收集，人只动嘴）

触发后按顺序做，**意图问人、技术细节自己拍板**：

1. **目标**——问用户一句话级别的目标 + 什么算完成。意图只有人知道，不清楚就停下来问，把困惑点具体说出来，不要猜。
2. **验证命令**——**自己找，不要先问人**：翻 package.json scripts / Makefile / CI 配置 / 项目 README，找到候选后报给人一句确认（"我打算用 `pnpm test` + `pnpm type-check` 做判定，OK？"）。实在没有才问；项目缺测试就明确建议先补测试再进 loop，不硬上。
3. **判定标准**——每条验证命令写清什么算过（exit 0 / 失败数为 0 / 输出含某标志）。模糊的判定标准等于没有。
4. **轮次上限**——默认 10，不问人。用户主动提了成本要求才调整。
5. **适用性判断**——目标不可机械验证时，**明确说不适合 loop + 给替代建议**（走方法论常规流程 / 先补验证手段），不把判断推给人。

收集齐后：复制 `模板-LOOP.md` 到项目根，命名 `LOOP.md`，填好头部，过 gate。

---

## 进 loop 的 gate（硬条件，不可绕过）

<阶段 gate>
- [ ] 目标一句话写清，且有明确的"什么算完成"
- [ ] 至少一条可执行验证命令 + 判定标准，已经用户确认
- [ ] 验证命令**当前真实跑过一次**，基线状态已贴进 LOOP.md（知道起点有多少错，才能判断每轮有没有进展）
- [ ] 验证命令质量过了一眼：不是恒真断言、覆盖得到目标关键路径
- [ ] `LOOP.md` 已建好，头部填完
</阶段 gate>

任一不满足就停下来处理，不进循环。

## 循环体协议（每轮固定动作）

```
1. 读上一轮账本（错误指纹 + 下一轮计划）
2. 动手前 grep / Read 锚定本轮要改的代码段——不凭印象动手
3. 做最小增量修改（只为消掉当前错误，不顺手干别的）
4. 跑全部验证命令
5. 贴真实输出进账本（长输出可截关键段：最终统计 + 失败清单必须保留原文，不许改写）
6. 提取错误指纹，和上一轮对比
7. 判定：全绿 → 进收尾；有错 → 检查刹车条件 → 下一轮
```

**错误指纹**：失败用例名列表 / 错误码+文件位置列表，按固定方式排序后记录。作用是机械判断"这轮有没有真进展"——指纹变了是进展（哪怕错误数没少），指纹一字不变就是原地踏步。

**跨对话接续**：新对话或换 agent 时，读 `LOOP.md` 头部 + 最后一轮即可继续，不需要历史对话。账本就是全部状态。

---

## 刹车（两道，触发即停）

1. **轮次上限**：到达上限（默认 10）→ 停下汇报，给人三选项 + 推荐：继续 N 轮 / 换思路 / 人工接管。
2. **停滞检测**：错误指纹**连续 2 轮完全相同** → 停下汇报。不要用重试代替思考——汇报里必须写"我卡在哪、试了什么、怀疑根因是什么"，不是只说"卡住了"。

刹车停下 ≠ 失败。带着具体困惑停下来，比烧完 10 轮交白卷有价值得多。

---

## 可选增强：评估器用独立 subagent

默认 loop 是同一个 agent 自跑自验——靠 Red Flags 自律防"放水"。但有个已知规律：**agent 评自己写的活会偏宽**（Anthropic 长任务 harness 框架反复验证过这点，是它把"生成"和"评估"拆成两个 agent 的根本原因）。自律有上限，换个干净上下文的人来评更可靠。

所以高风险场景可以升级：**让一个 fresh-context subagent 当评估器**——它只看本轮 diff + 验证输出 + 判定标准，不知道生成者的思路，独立判断"这轮到底过没过、有没有放水改测试"。生成者自评说全绿、独立评估器复核确认，才算数。

什么时候值得上：判定标准本身容易被钻空子（弱断言风险高）、改动碰了核心逻辑、或这轮明显有"想让验证闭嘴"的诱惑。代价是多一次 subagent 调用的 token。**简单低风险的目标不必**——单 agent + Red Flags 够用，别为对齐而上结构。

## Red Flags（loop 专属反捷径表）

心里冒出下面任何一条——**停**。这是合理化，不是判断。

| 你心里想 | 真实情况 |
|---|---|
| "把这个断言改宽一点就过了" | 你在让裁判闭嘴，不是在修代码。改测试只有一种合法理由：测试本身错了——且必须在账本里显式记录"改了测试 + 为什么它原本就是错的" |
| "这个测试太边缘，skip 掉吧" | 同上。skip = 把红灯拔了说路通了 |
| "加个 try/except 就不报错了" | 吞异常是把问题推进暗处。fail loud 比账面绿更有价值 |
| "给这个字段配个 fallback 默认值就绿了" | fallback 掩盖的是配置或逻辑错误，循环结束后它还在 |
| "差不多了，先标完成" | 判定标准没全过就是没完成。诚实记账 |
| "这轮错误和上轮应该不一样"（没对指纹） | 对指纹是机械动作，不是感觉。指纹一样就触发刹车 |
| "顺手把旁边这个 lint 警告也修了" | 范围漂移。最小增量只为消当前错误，别的记下来收尾后说 |
| "输出太长，我总结一下贴" | 统计行和失败清单必须原文。总结无法复核 |
| "基线不用跑了，反正都是错" | 没有基线就没法判断进展，gate 不许过 |

## 收尾协议（全绿 ≠ 结束）

<阶段 gate>
- [ ] **独立对照一次**——全绿后换个方式核一遍，按场景选：亲眼读一段真实产物 / 换更狠的输入重跑 / 断言关键副作用真发生。防假绿灯：弱断言、mock 掩盖、单次孤证
- [ ] **diff 回看**——逐个改动问"这是目标要的吗"：顺手的风格调整、无关重构 revert；改过测试的，核对账本里有没有对应的"为什么测试原本是错的"记录
- [ ] **影响检查（按风险）**——判断词：改动会不会让别人读到的东西变了？改了共享逻辑/契约 → 搜下游引用核对；纯局部修复 → 不查，别上仪式
- [ ] LOOP.md 写完 `## 收尾核验` 段
</阶段 gate>

然后按"阶段性产出报告"格式出报告：**课题**（目标是什么、起点多少错）/ **为什么这么改**（核心修法 + 关键转折轮）/ **预期效果**（基线 → 终态对比表）。大白话，结论先行。

在方法论流程内使用时：报告摘要回写 `PROGRESS.md` 对应 Step（含轮数、测试统计），LOOP.md 可留作审查材料或删除。

## 与 AI开发方法论 的关系

- 方法论管**项目级长周期推进**（定位 → 设计 → 开发 → 审查），本 skill 管**单个可验证目标的冲刺**。
- 在方法论阶段三内：某 Step 满足适用条件时进 loop，loop 是 Step 内部的微循环，结束后回到 PROGRESS 记账节奏。
- 独立使用时：不要求项目有 项目定位.md / PROGRESS.md，LOOP.md 自包含。
- 引用走 anchor 名字（"详见 `模板-LOOP`"），不写文件路径——文件可能被复制到别处。

## 理论锚（这套循环不是拍脑袋）

本 skill 的核心做法和业界"Loop Engineering"是同一思想，几条已核实的官方事实，供建立信心：

- **"写循环"是 Claude Code 之父的实践**：他公开说现在主要工作不是手写 prompt，而是"写循环"；并称给 agent 一个能自查的验证反馈闭环，能把最终结果质量提升约 2-3 倍。
- **验证器是命门，不是仪式**：一个没有验证的开环 = "自信地批量产出错误的机器"。本 skill"验证器就是天花板""输出原文是事实"正是这条的落地。
- **agent 自评会偏宽**：Anthropic 的长任务 harness 框架把"生成"和"评估"拆成不同 agent，根本原因就是 agent 总会高估自己的产出。这是上面"可选增强：评估器用独立 subagent"的依据。
- **工具落地**：Claude Code 的 Loops 适合本地快速实验（终端关即停、最长约 3 天）；Routines 跑在服务端（终端关不影响），适合云端巡检、依赖更新等长期任务。入门建议从单页脚本 + 简单验证（pytest / playwright 断言）起步，跑 3-5 轮观察停止条件，再迁到 Routines 做周期巡检。

> 出处：Anthropic 工程博客《Effective harnesses for long-running agents》《Harness design for long-running apps》、The New Stack 对 Loop Engineering 的报道。具体数字会随产品迭代变化，需精确值时查原文。
