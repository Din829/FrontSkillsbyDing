# AI 开发流程：修改与验证

目标明确就用小循环推进，需要设计或高风险复核时再增加相应工作；原始证据保留，账本负责找到它。仍保持 v0.1，本次样本验证不等于生产可靠性证明。

## 课题与修改

原规则可能把报错位置变化当进展、把验证器建设卡在自己的启动条件里，并让明确的小功能和受阻任务承担不必要的流程负担。六份文档同步修正，保留原有四要素，不新增执行框架。

| 原问题 | 修改后的行为 |
|---|---|
| 指纹变化即进展、相同两轮即停滞 | 看行为改善或能缩小根因的新证据；总轮次上限仍独立生效 |
| 未建好的验证器被要求先完成校准 | 按构建 C 起步，出口完成校准与真实基线；不能拿环境错误充当业务失败 |
| 已明确的新功能也要先做完整方案 | 单项实现可直接开始；未知方向、多模块设计仍先做方案 |
| 对账对象不同却要求原始差集清零 | 同类比较或通过关系检查，差异有解释或明确阻断关联任务 |
| 小任务交付、批量审批和归档例外不一致 | 任务级账本可验收；已批准批量按约定放行；受阻可归档，但不能标完成或重置预算 |
| 旧绿灯被直接沿用、输出重复粘贴 | 续跑先核当前现场；原文可引用该轮保留的日志，归档后检查链接可达 |

预期是减少误停、无效重试和重复整理，同时保留人的目标决定权、关键验收、证据与预算。没有测出 token 或时间收益，不作提效倍数承诺。

## 实测与证据边界

| 检查 | 观察结果 | 能证明什么 |
|---|---|---|
| 进展反例 | 只插空行可改变指纹；同名失败测试可持续减少遗漏 | 指纹不能单独判断进展，不是模型误判率统计 |
| 旧任务续跑 | 当前代码被改坏时先重验；外部用例由 8/14 符合要求变为 14/14 | 该任务能识别旧证据失效并修复 |
| 从零金额模块 | 27 个预先固定的外部输入符合要求；浮点错误实现被拒绝 | 这些输入的实现与判定器有效；不能外推所有业务 |
| 批量局部阻断 | B=1005、C=-29，A 保持 blocked，原账本保留 | 可做部分继续，未伪造 A 或整批完成 |
| 类型与差异检查 | mypy strict、npm 类型检查、错误类型对照、git diff --check 完成 | 对应代码/目录检查有效，不把语法检查等同类型检查 |
| 最终独立 AI review | 未发现应阻断收尾的规则冲突或必要约束缺失 | 文档一致性判断，不是生产效果证明 |

试跑中确实出现了小功能被送去完整方案、受阻账本缺少交接路径的问题，执行者作了明确记录。之后修订规则并独立复核；不把执行者临场处理说成旧规则本来就完全顺畅。

执行者没有继承主对话，外部验收未递给执行者，但共享文件系统，没有操作系统级强隔离。本轮没有新旧流程完整 A/B、多模型或多日生产验证，各组结果不能相加成整体成功率。
