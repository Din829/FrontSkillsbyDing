## 如果你只有十分钟

这五条是我们付出代价最大、也最反直觉的：

1. **裁剪历史时绝对不能深拷贝** —— SDK 靠对象同一性判断"哪些是新条目"，你改副本会把占位文写回真源，造出孤儿工具调用，然后**这个会话永久 400**（§2）
2. **凡是"必须一字不差"的东西，放返回值和代码，不放提示词** —— 固定话术、合规文本、状态判定，全部机械化（§4）
3. **提示词是稀缺资源，加一条会稀释已有的** —— 有实测：往注入文加一句话堵漏洞，漏洞没堵住，反而让另一条规则的执行率从 9/9 掉到 6/9（§7）
4. **断连 ≠ 取消** —— "用户关页面 → 服务端感知 → 停止"这条链在真实链路上不成立，必须有显式停止端点（§5）
5. **"什么时候做"和"什么时候显示"是两件事** —— 能在展示层解决的，不要去改模型行为；教模型时机会把它的调用意愿一起削掉（§6）

## 0. 总表：SDK 到哪儿为止

SDK 给的是**循环**，不是**产品**。

| SDK 已经给你的 | 你几乎一定要自己补的 |
|---|---|
| agent loop（模型 ↔ 工具的多轮调度） | 会话级并发控制（同一会话不能同时跑两个 run） |
| 工具的 schema 生成、参数校验、并行调用 | 工具的**状态契约**（失败/禁用/取消要能被机械识别） |
| 流式事件（文本 delta、工具调用、工具结果） | 事件到你自己前端协议的翻译 **+ 实时性修补** |
| Session 协定（历史读写接口） | Session 的**实现**，以及配套的预算裁剪 |
| Hooks（工具开始/结束回调） | 长任务心跳、静默判定、进度上报 |
| `tool_not_found` 之类的容错开关 | 用户可见的停止能力（工具级 + 整轮级） |
| 模型调用的抽象 | 参数与模型的**成对配置**、厂商差异适配、缓存断点 |
| 一个默认的轮数上限（**默认值会咬人，见 §1**） | — |
| — | 长期记忆（SDK 完全不管） |
| — | 观测（每轮落库、失败分类、等待与成本） |
| — | 提示词的注入分层与实验纪律 |
| — | 代码执行类工具的沙箱与资源治理 |

一句话：**SDK 解决"让模型能连续调工具"，剩下的全是你的事。** 而生产上出问题的地方，九成在"剩下的"里。

## 1. 模型接入层

> **SDK 到这儿为止**：它帮你把消息发出去、把工具定义序列化、把响应解析回来。它**不知道**你的网关有什么脾气、不同厂商能接受什么参数。

### 参数必须和模型「成对」设置

推理档位（reasoning effort）最典型：

- 有的模型不给档位就**思考全开** —— 一句问候烧掉两百多个思考 token，首字延迟翻倍
- 有的模型系列**根本不接受最低档**，传了直接 400
- 有的模型开最高档会把输出预算全用在思考上，**正文 0 字**（裸探针实测）

做法：把「模型名 → 默认档位」写成一个函数，环境变量可覆盖。**不要让人在部署时手动配对**——忘配一次就是一次静默劣化。

### `max_tokens` 不传，网关可能替你填一个很小的值

实测踩过：不显式传，网关给某类模型默认填了 4096。后果不是"回答被截断"这么温和——**部分模型在输出上限用尽于工具参数中途时，会把整个参数对象丢掉，返回一个干净的空 `{}`**（3/3 复现，不是残缺 JSON，是完整的空对象）。于是需要长参数的工具（比如一次生成十几页大纲）变成**确定性连续失败**，日志上却只显示"模型没给参数"。

做法：显式传各模型**官方规格的最大输出**。这个值不是"保守上限"，是模型的能力本身——别自己发明一个数字去造截断层。

### 🔴 SDK 的默认轮数上限会杀死工具链

SDK 通常有个默认的 `max_turns`（我们遇到的是 10）。听起来很宽松，但实测：**串行三个工具就已经是 4 轮**，而现实中稍复杂的分析题本来就要 2-3 轮，加上代码执行工具的"报错→改代码→重跑"循环，很容易撞上限。

撞上限的表现是**整个 run 抛异常**——用户看到的是一句英文内部错误，前面已经生成的部分内容全部悬空。

做法两条：

1. 把上限调到"现实题的十倍"（我们设 25），暴走防护仍然保留
2. **撞上限时不要当错误处理**，而是正常终止：把已有的部分正文吐出去，加一句"分析步数达到上限，请把问题拆开再试"

### 强制工具调用的隐性代价

`tool_choice=required` 在 SDK 设计上意味着"这一轮只能吐 tool_call，不能吐正文"。工具跑完后模型要**再起一轮**从头生成回答——串行两段，首字延迟实测多出 12～20 秒。

而且部分厂商**不允许强制工具调用和推理档位同时传**（扩展思考与强制工具互斥），组合起来直接 400。

做法：默认 `auto`，靠提示词约束"先取材再回答"。实测改好提示词后，刁钻问题上的捏造率是 0/4 —— required 的防幻觉收益能被提示词替代，它的延迟代价替代不了。

### 给不同厂商剥掉它不认识的字段

SDK 会给每个工具定义都加上某个厂商特有的字段。以前网关帮忙剥掉，某天网关改版不剥了，于是**该厂商模型 + 工具调用全部 400**。

做法：在客户端层按模型名前缀做规范化——"只发给这个厂商有意义的字段"。网关将来修好了也无害，因为那个字段对它本来就没意义。

### 缓存断点要用「累积规则」

部分厂商的托管模型**不支持自动前缀缓存，必须显式声明断点**。天真做法是只给 system 打一个，但那样每轮的历史和工具结果都在按全价重读。

断点也要打在消息序列上，规则必须满足：**位置能从当前消息列确定性地重新推导，且序列变长时旧位置不移动**。可用的三类位置：最后一条用户消息、已完成轮次的边界（后面紧跟 assistant 的 tool 消息）、序列末尾。超过厂商上限（通常 4 个）时**从前往后取**，别取最新的几个——保证下次调用还会选中同一批。

几个实测事实，省得你重测：

- 少于约 1024 token 的内容会被静默跳过，不报错，无害
- 开了推理档位时，**写进去的缓存条目要约 1 分钟后才能被另一种形状的请求读到** —— 所以同一轮内几秒一次的工具循环基本读不到，真正吃到红利的是**跨轮**（轮间隔通常大于 1 分钟）和**长达一分钟以上的单轮**
- 没命中的代价只是写入时的溢价，而且这个条目会成为下一轮的资产

### fallback 要知道什么时候闭嘴

主模型超时/5xx 切备用模型，这个没问题。两条边界是血的教训：

1. **已经吐出正文就绝不 fallback** —— 否则用户看到"半截回答 + 另一个模型从头重写"拼在一起
2. **SDK 的语义错误（如轮数超限）不是模型故障** —— 换模型重跑只会撞同一个上限，白等一倍时间，最后还用"模型故障"的文案误导用户

还有一个至今没补的洞：**fallback 只对"抛异常"发火，对"空流"无效**。实测某快模型在并发下约 20% 概率工具正常跑完、正文 0 字、状态成功（同条件高智能模型 0/10）。这类"空成功"绕过了所有错误路径。（现状是运营上避开该模型，机制上的门尚未补——**已知未解**。）

## 2. 上下文管理

> **SDK 到这儿为止**：它给了 Session 协定（读/写/弹出历史）和一个"入模型前改写"的回调点。**实现是你的，预算策略也是你的。**

### 两层历史必须分开

- **展示用历史**：用户在界面上看到的对话本文
- **模型输入历史**：包含工具调用与工具结果的完整条目流

只留前者，模型下一轮就丢了上轮检索到的素材（"上面那个数字"答不出来）；只留后者，界面会漏出内部标记。**两张表，各管各的。**

### 预算裁剪：三段式

1. 估算在预算内 → **一个字都不动**（这是最常走的分支）
2. 超了 → 从最老的开始，把保护窗（如最近 6 轮）**之外**的工具结果替换成占位文，**但保留工具调用本身**
3. 还超 → 整轮丢弃最老的（通常到不了这步）

第 2 步的关键是"只换结果、不删调用"——删了调用就出现孤儿的工具结果，部分厂商的接口做调用/结果配对校验，直接 400。

### 🔴 绝对不要在裁剪回调里深拷贝

整份文档里代价最高的一条。

SDK 判断"这一轮有哪些新条目要入库"，用的是**对象同一性 + 内容比对**。你在回调里深拷贝再改再返回，SDK 认不出那是历史，于是**把你占位文化之后的旧工具结果当成新条目写进真源**。下一轮读出来，工具调用和结果对不上 → 孤儿 → 400 → **这个会话此后每轮都 400，永久损坏**。

正确做法：**原地改**。SDK 传给回调的历史本来就是它深拷贝出来的牺牲副本，改它是安全的，也只有改它才能保持对象同一性。

### 估算函数会骗你，但不一定要修

用「字符数 ÷ 3」估 token 是英文假设。CJK 语言实测约 1.1 字/token，也就是**这个公式在中日文场景低估约 2.7 倍**——名义"5 万 token 预算"实际放行了约 13 万 token 的历史。

要不要修？我们选择**先记录不修**：改成准确估算等于"立刻开始更狠地裁剪"，是行为变更而非修 bug。**把实测值写在常量旁边，比悄悄改掉更重要**——不然下一个人会按字面意思去调这个数。

⚠️ 但这个偏差有个前提：**默认预算是按 20 万 token 上下文窗口定的**。往模型选择器里加一个 12.8 万窗口的模型时，光历史就可能撑爆窗口。**换模型时这是必检项。**

顺带一个性能坑：裁剪里如果每处理一轮就重新序列化整个历史来估算，就是 O(n²)。实测 400 轮的会话要 8 秒，99.7% 时间花在序列化上。而会话只会越来越长，不会回头。**只全量估一次，之后按改动量加减。**

### 被裁掉的内容要留一个取回口

裁剪之后模型对"最开始那个数字"就够不着了——只能重新检索（贵、结果会飘）或者凭记忆编（事故）。但**完整原文还躺在你的会话条目表里**。

做法：开一个历史检索工具，支持关键词检索 + 按编号取全文。权限（会话范围、身份判定）**全部在代码侧**，模型不经手任何 ID。

一个提高发动率的技巧：**把占位文本身写成对该工具的引导语**（"内容已省略，需要原文可用 X 工具按关键词取回"）。模型看到占位文的那一刻，正是它该调那个工具的时刻。改一个常量就行，裁剪逻辑一行不动。

诚实提醒：这个工具的**发动率天然很低**，因为裁剪只在长会话里发生。它是安全带不是引擎，别拿日常使用频次去衡量它。

## 3. 长期记忆

> **SDK 到这儿为止**：它完全不管。记忆是纯自建。

### 两条轨道，分工不同

- **即时轨**：会话中模型主动调工具记下来。管"即时性"——用户说"以后用 X 口径"，下一轮就生效
- **离线轨**：后台在用户静默一段时间（如 2 小时）后回顾整段对话，补记那些"反复自然出现但从没明说过"的偏好。管"覆盖率"

实测过两轨的差集：即时轨在"用户明说/纠正"上几乎不漏，但在"同一个口径反复用却从没明说"这类场景上是 0/6，而离线轨是 5/6。**两条都要，一条替不了另一条。**

离线轨的几个实现要点（都踩过）：

- **扫描单位是"人"不是"会话"**，否则同一用户的多个会话会并发重复抽取
- **分块要串行**，并且把前一块已确定的条目喂给下一块当"已有记忆"，否则块间重复
- **两种失败要反向兜底**：安全审查挂了就**不存**（fail closed），去重挂了就**存**（重复比静默丢失轻）
- **要有墓碑**：用户手动删掉的条目，必须记录"是被本人删的"，否则后续会话会把同样的内容原样抽回来（生产上真的复活过）。而且只有"本人删除"才算墓碑——系统合并/审计退役的不算，否则自愈能力也一起没了

### 注入位置：每轮的用户消息，不是 system

三条理由，都有实证：

1. system 要保持全用户一致，才能跨用户共享缓存
2. 长对话里 system 开头的风格指令**会衰减**
3. 消融实验反复验证：**每轮注入块的权威最高**

### 🔴 入库口必须剥除

每轮注入的记忆块，在写入会话条目表之前必须剥掉。不剥的后果：10 轮攒 10 份重复，而且旧记忆块留在历史里会**和当前注入的记忆互相矛盾**。

先说一条弯路：直觉上应该在"入模型前的回调"里做瞬态注入（注进去但不落库）。**这条路已被证伪**——SDK 会把回调返回值里所有它认不出是历史的条目**全部持久化**。唯一可靠的遮断点是**写入口**。

同一个道理适用于附件：base64 的图片/PDF 如果原样存进会话条目，会每轮原样回放，几轮之后请求体超过网关上限，然后**永久 400**。也在写入口换成占位文。

配套细节：用户输入里如果恰好含有你的块起止标记，剥除会吃掉正文。**注入前对用户输入做一次无害化**（把标记的括号换成半角之类，意思不变）。

### 记忆 fail soft，历史 fail loud —— 刻意相反

- 记忆读写失败 → 静默继续。最坏结果是"变回初次见面"
- 会话历史读写失败 → 直接抛。历史坏了模型会**自信地答错**

不要为了"统一风格"把这两个拉齐。

还有一条细节值得抄：**"功能不可用"和"用户自己关掉了"必须分开回复**。合并的后果是——数据表还没建好的环境里，系统告诉用户"你把记忆关了，去设置里打开"，而用户去看设置发现本来就是开的，**根本无从下手**。

### 一个反直觉的实测：细则要放工具说明，不要放注入文

我们想堵一个漏洞（用户把事实包装成"希望你这么看待"来绕过记录范围禁令），于是往每轮注入的规则文里加了一句话。结果（真链路，快模型，各 9 发）：

| | 加之前 | 加之后 |
|---|---|---|
| 违规记录 | 1/9 | 2/9（**没减少**） |
| 该记的漏记 | 9/9 全记 | **6/9**（口径纠正掉了 3 次） |

**净负**。但同样一句话放到**工具的 description** 里，该记的是 12/12，一点没伤。

这不是孤例，是第三次撞见同型现象。**结论：每轮注入文是稀缺资源，往里加东西会稀释已有条款的强制力；范畴细则应该放工具说明。**

## 4. 工具设计

> **SDK 到这儿为止**：它管 schema 生成、参数校验、并行调用、把结果塞回对话。**工具的语义契约是你的。**

### 全部常驻，而不是按需隐藏

我们最初按用户开关动态裁剪工具集合，结果：被关掉的数据源，模型从提示词里知道它存在，就去调 —— 工具不存在 → SDK 抛"tool not found" → 模型看到一句英文内部错误 → **自己推断成"系统故障"，向用户道歉**。

改成：**工具永远挂着，被关掉的源由工具自己返回一句固定应答**"这个源被用户关闭了，不是故障"。模型于是能准确表达"你关了这个源"。

有一条边界：**"天生没有的能力"用组合层隐藏，"用户关掉的能力"用固定信号回答**。两层不能混。

### 用固定前缀做状态契约，别让模型复述

工具返回值的前缀就是状态机的输入：

```text
（工具执行错误）...    → 前端标红，模型可切换其他源
（此源已关闭）...      → 前端另一种样式，不是故障
（技能建议）{json}...  → 框架据此确定性地发出一个 UI 事件
用户已停止此工具...    → 取消态
```

核心原则一句话：**凡是"必须一字不差"的东西，都放在返回值或代码里，不放在提示词里。** 合规文本、免责声明、固定话术，全部由代码机械拼接。实测教训：某个成果物的出处标注写成"请在合适位置自然地注明"，结果就是有的轮次写、有的轮次不写。

⚠️ 顺带一条容易忽略的：**这类"必须贴上去"的东西，判定作用域往往不是"这一轮"而是"这个会话"**。实测踩过——第一轮做分析、第二轮说"把它做成文件"，第二轮的上下文对象是全新的、检索记录是空的，于是标注一个字都没贴。修法是把判定升到会话级（进程内缓存加速 + 数据库兜底）。

### 🔴 "件数"这类语义，默认值要倒向安全侧

一个很小但反复复发的坑。工具返回值要在界面上显示"命中几条"，通用做法是数结果里的条目标记。但**非检索类工具**（代码执行、文件生成、记忆写入、技能应用）根本没有这个标记，于是通用计数返回 0，界面显示 **"0 件"** —— 用户看到的是"失败了/没数据"，实际是成功了。

我们的修法一开始是**逐个登记例外**："这个工具不算件数、那个也不算"。结果**漏了四次**——每加一类新工具就漏一次，而且漏了不报错，只是界面上多一个看起来像失败的东西。

最后改成：**默认倒向"没有件数概念"，只有真的检出 0 条时才显示 0**。以后再加什么工具都自动正确。

**通用教训：例外登记制一定会漏。能把默认值倒向安全侧的，就不要维护清单。**

### 委托型工具：让副模型执笔

对于"要生成几万 token 长文本"的工具（网页、文档、幻灯片），不要让主模型自己写在工具参数里。改成：**主模型只写 brief + 数据摘录，工具内部调一个廉价高速模型去写正文。**

四点收益，都实测过：

1. 主模型写超长工具参数期间，流式通道**完全静默**（这是长任务失败的主因）—— 委托后这个静默从结构上消失
2. 快（同题实测执笔时间从 95 秒降到 57 秒）
3. 便宜（执笔模型单价低，且省了主模型的输出 token）
4. 执笔是"文字进、文件出"的单发任务，不需要工具调用和判断，正好避开小模型的 agent 弱项

一个配套坑：**主模型会自作主张往 brief 里写配色要求**，而 brief 的指令会压过执笔侧的设计规范（遵守度从 1.0 掉到 0.2，自造颜色十几二十种）。修法是在工具说明里明确禁止写配色 —— A/B 实测：自发配色 6/6 → 0/6，而用户本人明确要求配色时仍能 2/2 传达。

### 子 agent：agents-as-tools，不是 handoff

主 agent 写"任务书"列表，工具内部并行跑若干调查型子 agent，各自返回带证据的结构化报告，**结论和取舍仍由主 agent 做**（不轻信二手信息）。

三个实现要点：

- 子 agent **共享同一个请求上下文对象**，所以引用编号是全局连号，并行也不冲突。**编号一定要在请求级统一分配并加锁**——按工具各自从 1 开始编号的话，同一轮里多次检索会撞号，下游按编号反查会指到别的文档上（我们真出过引用错位）
- 但**"编号正确"和"标记格式正确"是两回事** —— 子 agent 没拿到主提示词里的引用格式规范，会自造格式。修法是在报告出口用真实检索数据**机械改写**成标准格式，而不是叮嘱模型
- 甜点区是**"广度 × 深度 > 单个上下文容量"**，不是"任务多"。实测十家以内的深挖、二十家以内的浅扫，主 agent 自己做更快更省

### 代码执行工具的沙箱

如果你给 agent 一个"执行代码"的万能口（强烈建议——它能替掉几十个专用工具），安全**必须靠架构保证，不能靠提示词**。四层：

1. **进程隔离**：不在主进程 exec，起独立子进程
2. **干净环境变量**：白名单放行（路径、语言、后端类型），**API 密钥、数据库连接串一个都不给**
3. **资源上限 + 超时**：地址空间、CPU 时间、单文件大小，加上子进程超时
4. **一次性工作目录**：每次执行建临时目录，结束后收走产物再整个删掉

几条只有实跑过才知道的：

- **资源上限会和库的默认并行度打架**：在多核节点上，数值计算库 import 时会按核数起线程，**光线程栈的虚拟地址空间就撑爆地址空间上限**，于是"import 数值库"这一句确定性失败。修法是把线程数环境变量固定为 1。⚠️ **而且必须在子进程启动前注入**——写在用户代码里已经太晚（前置初始化代码会先 import）
- **输出洪水要折叠，但 stdout 和 stderr 要区别对待**：警告通道可以把"只有数字不同"的近似重复也折掉（某些绘图库的字体警告会刷几百行、上万字符）；**标准输出不能这么折**，因为那可能是数据本体，数字归一会把表格的不同行误判成重复
- **产物要双限（件数 + 总大小），而且丢掉的必须告诉模型**：只限件数的话，几个大文件照样撑爆传输；而**静默丢弃的后果是模型以为东西已经送到了，写出"如图 6 所示"，但用户那儿根本没有图 6**
- **跨调用缓存要自带 TTL 和身份键**：一次性工作目录意味着每次都从零开始，重复读同一个大文件很贵（实测 22MB 表格重复读要 17 秒，缓存后 0.1 秒）。但**持久化的那一刻，垃圾也一起持久化了**——所以 TTL 要在第一版就同期加上，不要留到以后。缓存键必须包含**文件大小和修改时间**，否则用户重传同名的不同文件时会静默返回旧结果（不报错，最难发现的那类事故）
- **同样的机制不要用提示词实现**：我们试过在注入文里建议模型"多次处理时先缓存"，文面确实送到了，但**一次都没被采纳**——因为措辞是条件式（"需要多次处理时"），而模型在写第一次代码时认为自己一次就能搞定，条件永远不成立。**能用机械手段做到的，就别指望模型自觉。**

### 工具数量要治理，但判据不是数量

到二十来个工具时我们做了一次治理，用三个仪表：

1. **选错率**（题库实测）
2. **常驻工具说明的总字数**（这是每次请求都付的税）
3. **易混淆的工具对**

三道防线：

- **准入四问**（加新工具前必须书面回答）：能不能不加？说明多少字、和最近的工具边界能否一句话切开？在场条件是什么？代价记在哪？
- **在场裁剪**（按侵入性从低到高）：条件性说明段 → 工具级在场开关 → 按场景组合
- **触发线**：选错率破零 / 出现新混淆对 / 说明总字数超阈值 / 某工具长期零调用

一个实测的正面案例：某工具的"修改用法"说明，只在"上一轮确实产出过东西"时才挂载。常驻时，同一段说明里另一个条款的执行率从 77% 掉到 53～67%。**同居的说明互相稀释，这是可测量的。**

### 能力包（skill）用数据驱动，不要写进提示词

把"定型作业流程"做成一个个 markdown 文件（前置元数据 + 正文），启动时扫目录加载：

- **发现层**放在一个工具的 description 里（由元数据自动生成清单）——这样 system 提示词**一个字都不用改**，加一个能力就是加一个文件
- **正文按需注入**到当轮的用户消息里，而不是常驻 system
- 元数据里留一个"内部"标记，标了的不出现在用户可选清单里，但仍可由程序指定调用

这和主流 agent 产品的 skill 机制是同一个语义（元数据常驻、正文按需、正文按用户输入对待），在只支持 chat completions 的接口上也能实现。

## 5. 运行时控制

> **SDK 到这儿为止**：它能跑完一个 run，也能被取消。**但"用户点了停止"这件事怎么到达它、停止之后残局怎么收拾，全是你的。**

这一节几乎每条都来自生产事故。

### 会话级串行锁

真实事故：用户在长任务跑到一半时打了句"好的我等着"，客户端把它当新消息发过来，**第二个 run 起来了，用户收到两份产物**（两个 run 实测重叠 99 秒）。

从 agent 侧防不住：SDK 写会话条目是以 run 为单位的，进行中那一轮还没有任何记录；上层"我还在做"的提示也进不了模型输入。**唯一的解法是不让第二个 run 起来。**

三个实现细节：

- 锁的键是"一段连续对话"的锚，不同入口的锚各自独立
- **锚为空时不加锁**。有条路径会传空字符串，拿空串当键的后果是"所有无锚会话共用一把锁 = 全局串行"
- **不要加 TTL**。`finally` 是唯一释放口（取消、断连都会走到），进程死了字典也没了，自然自愈。加个"保险起见 N 分钟自动释放"反而造出新病：**正常的长 run 被误杀**

被锁挡掉的那一轮，要**当作没发生过**：不启动 agent、不写会话条目、不写库，只回一句"上一个请求还在跑"。否则会污染正在跑的那一轮的上下文。

### 工具级停止：必须返回，不能抛

直觉是给工具协程抛取消异常。**别这么做**——它会穿透 SDK 内部的异常处理，把**整个 run 弄死**，而需求是"停掉这个工具、agent 继续活着"。

正解：工具自己检查一个事件，然后**把固定文案作为正常返回值 return**。文案里连行动指令一起写上（"不要自动重试，等用户下一步指示"）——因为**指令必须放在数据里**，写在提示词里守不住。

另外要支持**预取消**：用户可能在模型还在写工具参数（工具尚未启动）时就点了停止。做法是取消端点即使找不到对应工具也**先把事件建好并置位**，工具启动时第一件事就是检查，然后立刻自杀。

⚠️ 但**会话级的旗子绝对不能做预取消**：工具级的键是一次性的调用 ID，用完即弃；会话锚会复用，残留的旗子会杀掉用户的下一个问题。

### 整轮中止时，要主动叫醒所有工具

如果某个工具是在**线程里跑子进程**（比如代码执行沙箱），那么取消协程**杀不掉它**——线程和子进程会一直跑到自己的超时（比如 120 秒）。

做法：整轮中止时，遍历该会话所有已登记的工具事件并置位。**这样不需要给每个工具单独接线，已登记的工具全都会停**，以后新增的工具自动享受。

### 🔴 断连 ≠ 取消

最反直觉的一条。"用户关掉页面 → 连接断开 → 服务端感知 → 取消"这条链，**在真实链路上不成立**。

我们本地 A/B 过：客户端直连服务端然后断开 → 0.0 秒内工具收到取消，**说明我们的代码是对的**；中间加一层"不把断连传下去、写入也不报错"的转发 → 工具一路跑到底、正常完成、锁一直被握着 —— **生产症状逐条复现**。（那层具体是谁至今没定位，属于**已知未解**。）

结论：**别依赖 TCP 断开，要有一个显式的停止端点。** 而且停止旗要挂在会话锁上，因为只有锁的 acquire/release **精确括住了一个 run 的生存期**，旗的寿命才不会跨到下一轮去误杀。

### 心跳，以及区分"正常静默"和"故障静默"

模型在写超长工具参数时，流式通道会**一个字节都不发**。而下游（客户端、网关、反向代理）通常按"字节间静默"计算读超时。所以要每隔一段时间（如 20 秒）插一个协议层的注释行——所有正规的流式消费端都会无害地忽略它。

但心跳带来新问题：**故障时心跳照常流，前端看起来一切正常**，用户只能干等。生产实录里有过上游静默 3 分 14 秒然后断开、产物为零。

所以还要有静默判定。关键是**正常的静默确实存在**（图像生成期间实测静默 148 秒），一律报警就是天天说谎。切分依据：**工具是否真的进入了函数体**（用取消登记表判断）。于是变成两档阈值：

- 工具没启动的静默 → 较短阈值（如 90 秒）就提示
- 工具在跑的静默 → 较长阈值（如 180 秒）才提示，因为长任务本来就该慢

更好的做法是让长任务工具**自己打心跳**：把"等待"包一层，每 N 秒上报一次已用时间。这样只依赖一个"上报口"，任何工具包一下就有心跳，**不需要维护"哪些工具需要心跳"的登记表**（又一次避开了例外登记制）。上面那个双档阈值就退化成给还没接心跳的工具兜底。

### 中止之后的残局

被中止的那一轮，要往**两个地方**写东西，因为用途不同：

1. **展示用历史**：让用户回看时知道"生成到哪儿、为什么断的"
2. **会话条目**：让下一轮的 agent 知道"用户主动停了，不要自作主张续写或重跑"

不写第 2 项的话，下一轮 agent 看到"问题没被回答"，会热心地自己补答一遍。

两个易错点：中止路径里**不要 await**（取消上下文里下一个 await 可能立刻被再取消）；**锁要在写库之前释放**（写库可能耗秒级，握着锁会让用户"停止后立刻再问"被拒）。

## 6. 流式与前端契约

> **SDK 到这儿为止**：它给你一串事件。**但这串事件的时序不等于用户该看到的时序**，而且有些关键时刻它给得太晚。

### SDK 的工具结果事件会"等齐"，要用钩子抢在前面

SDK 的工具结果事件是**整轮所有工具都跑完才一起进队列**的。并行调五个工具时，最快的那个（0.3 秒）也要等最慢的那个（20 秒）才在界面上变绿——用户看到五个转圈的点同时停下，体感很差。

修法：用 SDK 的**工具结束钩子**（`on_tool_end`）。它是在每个工具自己的协程里 await 的，**谁先完成谁先触发**。把钩子的通知和 SDK 的事件流**汇进同一个队列**，出口顺序就等于真实发生顺序。

同理，**"模型决定要调某个工具"这个时刻，原始事件流比正式的工具调用事件更早**（实测早 0.03～4.76 秒，参数越长差得越多）。要抢时间显示"开始调用"，就监听更底层的那个事件。

### 让工具能往流里插播

长任务（出图、并行子任务）跑起来之后，**SDK 一个事件都不会发**。想显示"3/6 完成"就必须让工具**主动往流里插播**。做法是把队列作为上下文对象的一个可选字段传下去，工具调一个 `emit_progress` 就行——没有队列时就是空操作，测试和其他调用路径完全不受影响。

⚠️ 进度信息属于**界面临时状态**，不要混进"工具记录"里——那个记录会进元数据、落库、并在历史回放时重现，混进去就是把内部状态泄漏到持久层。

### "做的时机"和"显示的时机"是两件事

这条价值很高。

我们有个"能力建议卡片"：agent 判断当前话题适合某个定型流程时，调一个工具，前端弹一张卡让用户确认。问题是 agent 会把这个工具**和检索工具一起在开头调**，于是卡片比正文先到——按发生顺序插的话，用户看到的是"卡片刚出现，AI 就自顾自开始写长文"，而这期间点"使用"是**没反应的**（请求还在进行中）。实测这个尴尬期：快模型中位 15.7 秒，高智能模型中位 33.2 秒、最长 52.2 秒。

直觉修法是教模型"写完正文再调这个工具"。**实测否决**：建议率从 100% 掉到 12.5%（快模型）、87.5% 掉到 50%（高智能模型）——**教它时机，会把它的调用意愿一起削掉**。

正解：**呼叫时机交给模型，显示时机由前端决定**。前端把卡片信号暂存，等正文写完再插到末尾。零提示词改动，零副作用。

**推广一下：凡是"模型行为本身没错、只是顺序不好看"的问题，先在展示层找解法。**

### 协议演进要向后兼容

两条具体做法：

- **附加信息用可选键**：给已有的事件加字段，旧客户端读不认识的键会直接忽略，**契约不变**
- **不要轻易发明新的状态值**：我们要表达"上游卡住了"，本可以加一个新状态，但旧前端遇到未知状态**会生出一行新的工具记录**（因为它的逻辑是"没见过就新建"）。改成复用已有的"运行中"状态、往里加一个字段，旧前端只会当成一次无害的刷新

推论：**设计协议时就该规定"未知值怎么办"**，否则每次演进都要担心老客户端。

### 前端也要有看门狗

服务端心跳解决的是"下游把我当超时"，但解决不了**半开连接**：中间某一跳断了，服务端以为还连着，客户端的读操作**永远不会返回**（实测有前端空转 14 分钟的记录）。这种情况只能前端自救。

关键设计：**看门狗只在"这个流已经见过至少一次心跳"之后才武装**。因为"90 秒没有字节 = 异常"这个前提，只在有心跳的流上成立；对没有心跳的旧接口，武装了就是误杀。**用机制保证，而不是靠人记得"这条路不要开看门狗"。**

### 结束状态要在前端穷举

工具的终态不只有"成功/失败"，还有"被用户关闭""被取消"等。**漏掉任何一个，那一行就会一直转到流结束**——已经结束的东西却顶着"进行中"的脸。

## 7. 提示词与动态注入

> **SDK 到这儿为止**：它把你给的 instructions 原样发出去。**分层、时机、稀释效应，全是你的事。**

### 三层结构

| 层 | 放什么 | 变化频率 |
|---|---|---|
| **静态 system** | 铁则、角色、回答骨架、引用规范 | 每天最多变一次（如果带日期） |
| **场景静态追补** | 只在特定入口成立的格式细则 | 按场景固定 |
| **每轮用户侧注入** | 记忆、当前对象、附件、场景行为锚、人格锚 | 每轮 |

分层的理由是**缓存**：system 保持全用户一致才能跨用户共享；把用户 ID、时间戳这类每请求都变的东西塞进 system，缓存就全废了。

如果 system 里要放日期，**放在最末尾**——前缀不受日变影响。粒度到天就够，缓存 TTL 通常只有几分钟。

### 追补的位置很关键，不是"追加到末尾"

场景追补要插在 system 里的**一个明确标记位**，不是拼在末尾。实测：追加到末尾之后，某个操作建议的发动率从 3/3 掉到 0/2 —— 因为它变成了"回答格式规范"后面的续文，注意力权重完全不同。

（标记位要始终被替换，没有追补时替换成空串。这样任何场景的提示词里都不会裸露出标记本身。）

### 🔴 收窄在场条件，优于加禁令

整份文档最想让你记住的一条。

现象：**同居的说明会互相稀释，而且加东西也会稀释。** 前面举过三个数字例子（记忆规则文加一句 → 该记的 9/9 掉到 6/9；工具修改说明常驻 → 另一条款执行率 77% → 53%）。

所以当你想"再加一条约束"时，正确的次序是：

1. 能不能让这条说明**只在需要的时候在场**？（条件性说明段、按场景挂载）
2. 能不能放到**更贴近使用点**的地方？（工具说明 > 每轮注入文）
3. 实在不行才是加禁令，且**加完必须 A/B 复测原有条款有没有退化**

### 稀释的另一种形态：规则之间会互相破坏

不只是"加了新的削弱旧的"，还有"改了这条，另一条复发"。

一个实测案例：某个生成规范原本对图表只有一句话，导致模型把不同量级的数据画在同一根轴上（读者会误读）。加了四条作图规则之后：

- 🟢 硬伤治好了（量级混载 2 件 → 0 件，第二根轴真的立起来了）
- ⚠️ 但软伤增加了（标签互相重叠 1 件 → 4 件——因为模型看不见渲染结果，**精确避让在原理上做不到**）
- 🔴 试图再补一条规则去治标签重叠，结果**另一条早就治好的病复发**（图例被拆成"盈利/亏损"从 0 件回到 4 件），只好撤回
- 🔴 **净值上接近相抵**："有瑕疵的产物"从 3/8 变成 4/8。治好的是硬伤、增加的是软伤，作为交换是划算的，但**用户根本看不出差别**

两个教训：

1. **一条规则一次只能治一种病，而且可能唤醒另一种。改完要把之前治好的都复测一遍。**
2. **判定器本身会骗你**：这个实验最初测出来是"71% → 23%"的灾难性结果，排查后发现是判定器有五个误判（其中一个是：第二根轴的标签对齐方式不同，判定器直接把整根轴看丢了）。**先修判定器，再看结论。**

### 注入措辞：写行为规则，不写状态断言

实测过一个消融：把注入块写成状态断言式（"当前 XX 未确定"），模型会**直接无视对话历史**（0/6）；改成"事前未指定 + 行为规则"（"遇到 X 就做 Y"），恢复到 12/12。

**注入块里禁止状态断言句式。**

### 参数说明是另一条通道（SDK 细节，很多人不知道）

工具级说明可以整体覆盖，但**参数级说明是从函数 docstring 的 `Args:` 段、经由 docstring 解析器另一条路进 schema 的**。

这带来一个很好用的实验方法：**工具说明本体一个字不动，只改参数说明做 A/B**，从而不惊动已经调好的发动率。

⚠️ 但有个隐蔽陷阱：解析器只在续行**比参数名那行缩进更深**时才拼接，**同级或更浅的续行会被静默丢弃**。也就是说，你为了排版整齐把缩进对齐的那一刻，参数说明的后半段就消失了——症状表现为"模型判断变差"，从任何聚合指标上都看不出来。

**保险做法：参数说明写成一整行**（几百字也没关系，单行不依赖缩进），并写一个测试固定它的首尾和长度。

### A/B 要怎么做才算数

一个真实案例的设计，可以照抄：19 道题 × 5 组 × 多模型 × 多入口，同时统计**两个方向**——该发动的发动了没有、不该发动的误发了没有。

结论很说明问题：

- 判断"是不是明确请求"本身模型不难，明确/同意类的题**三次跑都是 24/24，零抖动**
- **差异全在模糊题上**：去掉"拿不准就选否"和"两种错误代价不对称"这两句保守偏向，**误发动从 0 涨到 6**
- 而且不只是"倾向变了"，**调用本身也变得不稳定**（某道题三次都不调了）

教训：**保守偏向的措辞不是装饰。** 以及**只看单方向指标会得出相反结论**。

## 8. 观测

> **SDK 到这儿为止**：它有自己的 tracing，但通常指向厂商自己的端点，内网环境基本用不上（我们直接关掉了）。**观测要自建。**

### 每轮一行

一张表，一轮一行，字段大致是：用户、入口、模型与是否 fallback、用到的能力包、工具（名 + 状态 + 各自耗时）、产物**只记种类**、引用数、首字延迟、总时长、状态、错误类型。

### 三条红线

1. **不存问答原文**，只存元数据。原文在会话表里，用会话 ID 关联即可（分析与内容分离）
2. **失败、取消、空回答也要写行**。"没结果就不写"会让**正常和故障长成同一张脸**（我们吃过亏：某个数据源掉线两天，从水位线上完全看不出来）
3. **观测绝不能赢主流程**。守护线程 fire-and-forget，不 await；失败**记日志但放行**——握住但不沉默，这样表没建好时第一天就能发现

补充两个容易忽略的：

- **边界截断**：外部来源的用户 ID 可能逼近列宽，超一个字符整行写入失败，**那个用户从此在统计里完全消失**。在写入口截断
- **观测本身要能测到"等待"**：并发闸门的等待发生在你自己的进程里，云服务商的监控看不到。我们后来补了闸门埋点（等了多久、握了多久、要槽时前面排着几个）。**服务商侧限流为 0，不等于容量够——那可能只是你自己在门口就把人拦住了。**

### 上下文构成也应该落库

每轮记录"这一轮的提示词由哪些部分构成、各多少字"（system、工具说明总量、各注入块、裁剪后的实际历史）。这让"提示词调优"从事后手工考古变成可查询的数据。前面所有关于稀释效应的判断，靠的就是这类数据加 A/B。

## 9. 质量保障

> **SDK 到这儿为止**：它没有意见。

### 红绿破坏：新测试变绿只证明一半

必须**把旧实现放回去确认它变红**，不变红的测试什么都没守住。

两条配套纪律：

- 破坏要**机械确认打中了**（先断言"旧字符串确实在文件里"再替换），否则"没改成功"会伪装成"改了也没事"
- **别用版本控制的 checkout 做破坏实验**（会冲掉未提交的实现）——先提交，破坏和还原都用精确替换

### 假绿灯的常见形态

按吃过亏的频次排：

1. **弱断言**：测了一个永远不会失败的场景（例：想验证"某类条目被排除"，但那类条目本来走的就是默认丢弃分支，破坏了也还是绿的）
2. **测试互相投毒**：模块级往全局注册表塞替身，单文件跑全绿、合跑一片红。判别法是"逐文件合计"和"合跑"的差额。修法是并行时**保证同一文件在同一进程**
3. **mock 掩盖真实行为**：探针自己造的输入复现不了真实产物的问题
4. **判定器自己坏了**：把"崩了"读成"通过"——判定要落在退出码这类机械事实上，别靠字符串匹配。（§7 那个"71%→23%"就是活例子）
5. **拿调参用的题去验收**（等于用训练集自评）
6. **"什么都没做"被算成成功**

### 模型准入要有门槛层

新模型上线前跑一套体检，**第一层是一票否决**：是否支持函数调用、并行工具的索引对不对、推理档位接受哪些值、用量统计有没有透传、缓存声明能不能过、强制工具 + 推理档位的组合会不会 400、图像输入行不行。**这层不过，后面测什么都没意义**——因为它会在生产上变成 400 或静默故障。

后面几层分别是速度与准确度（首字/总时长、关键数值逐字命中、反幻觉、跨对象）、指令遵循、以及**人眼评审**（表达力这层机器测不了）。

两条实践：题库驱动、支持断点续跑；判定器改了之后能**重新判定已有输出而不用重跑模型**。

## 10. 提炼：十条可迁移的原则

1. **契约放返回值和代码，不放提示词。** 固定文案、合规文本、状态判定，全部机械化
2. **工具全常驻，不可用就返回"为什么不可用"。** 藏起来会让模型幻想故障
3. **要加约束时，先问"能不能收窄在场条件"**，其次"能不能挪到更贴近使用点的地方"，最后才是加禁令 —— 并且加完要复测老条款
4. **例外登记制一定会漏。** 能把默认值倒向安全侧的，就不要维护清单（件数语义、心跳登记，都是这么解决的）
5. **能用机械手段做到的，别指望模型自觉** —— 尤其是条件式的建议，模型在"条件成立之前"根本不会考虑它
6. **观测永远不能赢主流程**，但也不能沉默
7. **fail loud 还是 fail soft，按后果分，不求统一**
8. **别给"不可能发生的情况"加防御**，它会造出新的病（TTL 误杀正常任务是活例子）
9. **事实 ≠ 结论。** 工具返回空、指标为 0、测试通过，都只是事实，中间还差一层验证
10. **新测试变绿只证明一半**，把旧实现放回去变红才算数；说"不影响现有功能"之前，拿旧版跑同样输入逐项对照

## 11. 已知未解 / 还在验证

诚实列出来，免得读者以为这套东西已经收口：

- **进程内状态与多副本的矛盾**：会话锁、工具取消登记表都是进程内字典。副本数大于 1 且没有会话亲和时，停止请求可能落到别的副本上而空振。**结构上成立，尚未实测证实**（当前环境实际几乎一直是单副本）
- **"空成功"没有兜底**：fallback 只对异常发火，对"工具正常完成但正文 0 字"无效。已定位到与特定模型 × 并发相关，运营上绕开了，机制上的门还没补
- **断连被中间层吞掉**：具体是哪一层至今没定位，现状靠显式停止端点绕过
- **裁剪的估算偏差**：已实测、已记录、**刻意未修**（修了等于行为变更）
- **提示词的场景差异**：同一句措辞在不同入口效力不同（某个边界题在一个入口 0 误判、另一个入口 2/2 误判）。属于"任何措辞都不可能 100% 分开"的本质模糊区，计划靠真实频次数据再决定要不要动
- **生成物的软瑕疵**：模型看不见自己的渲染结果，标签重叠这类问题**原理上只能靠"少画一点"缓解，不能靠规则解决**
- **SDK 版本**：钉在一个较早的小版本上已有一段时间。没有发现破坏性变更，但也没有系统性跟进
