> 从 `agent-sdk.md` 路由过来。**把 agent 干活的过程实时展示给用户**时读这份。
>
> **来源**：<https://openai.github.io/openai-agents-js/guides/streaming/> ＋ `extensions/ai-sdk` 官方页

## 先分清三类事件

开了 `{ stream: true }` 之后，流里只会吐三种东西：

| 事件 type | 是什么 | 你多半要用它做什么 |
|---|---|---|
| `raw_model_stream_event` | 模型原始增量 | **判断正文开始吐字**（收起进度列表的信号） |
| `run_item_stream_event` | 运行期产生的条目 | **驱动工具调用列表**（增删改状态） |
| `agent_updated_stream_event` | 当前 agent 换了 | 多 agent 时更新"谁在干活"的标识 |

`run_item_stream_event` 用 `name` 区分具体是什么条目，共十种：

| `name` | 含义 |
|---|---|
| `tool_called` | 发起了一次工具调用 |
| `tool_output` | 工具返回了结果 |
| `tool_approval_requested` | 工具调用**卡住等人批准** |
| `message_output_created` | 产生了一条消息输出 |
| `handoff_requested` | 模型请求转交 |
| `handoff_occurred` | 运行时完成了转交 |
| `reasoning_item_created` | 产生了推理条目 |
| `tool_search_called` | 发出 `tool_search_call`（仅用 `toolSearchTool()` 时） |
| `tool_search_output_created` | 载入了延迟工具定义（同上） |
| `compaction_item_created` | 产生了上下文压缩条目（长流程才有） |

`agent_updated_stream_event` 直接给 `agent.name`。

> **注意**：官方 streaming 文档的表格只列了 9 个，漏掉了 `compaction_item_created`。以上 10 个取自源码 `agents-core/src/events.ts` 的 `RunItemStreamEventName` 类型定义。**遇到官方文档和源码打架，信源码。**

## 映射表：事件 → UI 动作

| SDK 事件 | UI 该做什么 |
|---|---|
| `run_item_stream_event` / `tool_called` | 进度组不存在则创建并展开；追加一条，置 **running** |
| `run_item_stream_event` / `tool_output` | 该条变脸 **done**（失败则 failed）；组进度 +1。要展示/断言返回值用 `item.output`（工具函数的原始 JS 返回值），`item.rawItem.output` 是交给模型的序列化串 |
| `run_item_stream_event` / `tool_approval_requested` | 该条切 **等待批准** 态，露出批准/拒绝操作 |
| `run_item_stream_event` / `handoff_occurred` | 插入一条转交标记；后续条目归到新 agent 名下 |
| `agent_updated_stream_event` | 更新"当前谁在干活"的标识 |
| `raw_model_stream_event` 且 `data.type === 'output_text_delta'` **的第一次** | **收起进度组**，变成汇总条 |
| 本轮结束 | 汇总条定格（带最终计数、耗时等元信息） |

### 🔴 收起时机必须判到 `data.type`，不能只判事件类型

`raw_model_stream_event` 是个大类，它的 `data.type` 有四个值，**只有一个是给用户看的正文**：

| `data.type` | 是什么 | 带什么 |
|---|---|---|
| `output_text_delta` | **给用户看的正文增量** | `delta`（文本）、`itemId` |
| `response_started` | 一次响应开始 | — |
| `response_done` | 一次响应完成 | 完整 `response` |
| `model` | **原始 provider 事件透传**（工具调用参数的增量走这里） | `event`（any） |

只判 `event.type === 'raw_model_stream_event'` 就收起列表，会被 `response_started` 和 `model` 抢先触发——工具还在跑列表就没了，用户看到闪一下。

```ts
// ❌ 会被 response_started / model 抢先触发
if (event.type === 'raw_model_stream_event') collapse();

// ✅ 只认正文文本增量，且只认第一次
if (event.type === 'raw_model_stream_event'
    && event.data.type === 'output_text_delta'
    && !collapsed) { collapsed = true; collapse(); }
```

**判断问句：这个 delta 是给用户看的正文，还是模型在填工具参数？** 分不清就会闪。

### OpenAI 专属事件的类型收窄

用 OpenAI provider 时，想安全地读 provider 专属负载（如 `response.reasoning_summary_text.delta`、`response.output_item.done`、MCP 参数增量），SDK 给了收窄助手：

- `isOpenAIResponsesRawModelStreamEvent(event)`
- `isOpenAIChatCompletionsRawModelStreamEvent(event)`

这些事件的 `source` 字段会是 `'openai-responses'` 或 `'openai-chat-completions'`。

**只写传输层无关的代码时，判 `event.type` 就够了**，别过度收窄——那会把代码绑死在 OpenAI 上。

## 五条 UI 铁律

映射对了不代表体验对。这五条是工具调用展示的通用骨架，**换什么视觉皮都不能破**：

1. **挨个出现** —— 工具通常是并行发起的，但显示上逐条滑入（间隔几百 ms），别一坨砸出来。
2. **并行独立变脸** —— 谁先跑完谁先标完成，不按入场顺序排队。
3. **running 必须有活着信号** —— shimmer、spinner、点阵闪动都行。**静止的"进行中" = 用户以为死机**，这条最不能省。
4. **收起时机 = 正文首个 token**，不是最后一个工具跑完。工具全完但 agent 还没开口时，列表继续摊着。
5. **条目之间连线** —— 细竖线串成垂直时间线，工具调用是一条链不是散行。

元信息分级：**进度 `x/y` 是主角**（常驻）；耗时、token 数、结果条数是**装饰**（可省，加了也是小字配角，不抢正文）。

无障碍：honor `prefers-reduced-motion`——开了就把"活着信号"退化成静态标记 + 文字"进行中"，别硬做动画。

## 别自己撸传输层：官方有现成的

`@openai/agents-extensions/ai-sdk-ui` 提供三个助手，把 agent 流直接接到前端路由：

| 函数 | 用在什么时候 |
|---|---|
| `createAiSdkUiMessageStreamResponse(source, options?)` | 路由直接返回 AI SDK 响应 —— **最常用** |
| `createAiSdkUiMessageStream(source)` | 你想自己掌控响应/渲染层，但复用官方的 `UIMessageChunk` 翻译 |
| `createAiSdkTextStreamResponse(source, options?)` | 只要纯文本流 |

`source` 收 `StreamedRunResult`、类流对象或兼容包装。`options` 可传 `headers` / `status` / `statusText`。

**取舍**：要做上面那套精细的工具调用进度 UI，往往需要自己消费 `run_item_stream_event`（helper 给的是标准化 chunk，粒度不一定够）。**先用 helper 跑通链路，需要精细控制时再降到裸事件**——别一上来就手撸。

仓库里有 `examples/ai-sdk-ui` 完整应用可以照着抄。

## 边界情况

- **流式中的人工审批**：`tool_approval_requested` 之后这轮流会**结束**（不是挂着等），`result.interruptions` 非空；你把 `result.state` 存起来，用户点了批准/拒绝后 `state.approve/reject` 再 `run(agent, state, {stream, session})` 开一条新流续跑。完整链路见 `对话式应用.md` 决策四。
- **中途停流再续同一轮**：官方 streaming 指南有专节，别自己造。
- **多 agent 场景**：`handoff_occurred` 和 `agent_updated_stream_event` 会成对出现，UI 上要让用户看出"换人了"，否则进度列表会显得莫名其妙。**`agent.asTool()` 不发这两个事件**——专家在嵌套 run 里跑，外层流只看到一次普通 `tool_called` / `tool_output`；要展示专家内部过程得用 `asTool({ onStream })` 自己转发（坑见 `对话式应用.md` 决策一）。

**上生产** → `生产层-经验总结.md` §6：心跳与静默判定（正常静默真实存在，按“工具进没进函数体”分两档阈值）、前端看门狗（半开连接靠服务端心跳救不了）、“做的时机和显示的时机分开”（教模型时机会把调用意愿一起削掉）、协议演进要规定“未知值怎么办”。
