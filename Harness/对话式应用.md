# 对话式 Agent 应用

> 从 `agent-sdk.md` 路由过来。做**聊天型应用**（独立聊天产品，或嵌进现有产品的助手面板/客服窗）时读这份。
>
> **来源**：官方 guides 的 sessions / orchestration / context / human-in-the-loop / realtime 五页 ＋ 源码核对
> **核对于 2026-08-18**，`@openai/agents` 0.16.1（同日四组盲测后补了决策四、五、图片输入、撤回一轮、asTool 事件）

对话式应用有五个决策必须先定，定错了后面很难改。下面五节各解决一个，最后是图片输入这类小事。

---

## 决策一：多 agent 怎么协作——`asTool` 还是 `handoff`

这是对话式应用最容易选错的地方，**两者的用户体验完全不同**：

| 模式 | 谁在跟用户说话 | 什么时候用 |
|---|---|---|
| **agents as tools**（`agent.asTool()`） | **主 agent 始终掌控对话**，专家只在背后做子任务，输出回到主 agent 手里 | 你要一个统一口径的答复、要在一处收口 guardrail、要综合多个专家的结果 |
| **handoffs**（`handoff()`） | **专家接管对话**，之后由它直接回复用户 | 路由本身就是流程的一部分（分诊台→专科），各专家要用不同的 instructions / 模型 |

**判断问句：这个专家 agent 的回答，该不该直接出现在用户眼前？**
- 不该（只是中间产物）→ `asTool`
- 该（它就是接下来对话的主角）→ `handoff`

**第二条判据（要把过程展示给用户时）：UI 上要不要显示"换人了"和专家内部的工具调用？**
- 要 → `handoff`。`agent_updated_stream_event` **只在 handoff 时发**（源码 `run.js` 只有 `next_step_handoff` 一处触发），专家的工具调用直接出现在外层流里。
- 用 `asTool` 的话，外层流从头到尾只有主 agent，专家内部事件要靠 `agent.asTool({ onStream })` 自己转发；`onStream` 是构造 agent 时绑定的，拿不到当前请求的上下文，要用 AsyncLocalStorage 时必须把 `run()` 调用本身包进作用域（只包"消费流"那段拿到的是 `undefined`，TS 不报错、转发静默失效）。

两者可以混用：分诊 agent 先 handoff 给专科，专科自己再用别的 agent 当 tool 做有界子任务。

**专家接手后只打招呼不干活**（实测三组独立撞到）：handoff 后专员回一句"已为你转接"就结束；asTool 的专员凭记忆编答案不调工具。instructions 里写明"用户的问题已在历史里，直接回答，别反问"；必须调工具的加 `modelSettings: { toolChoice: 'required' }`（`resetToolChoice` 默认 `true`，用过一次后自动弹回，不会死循环）。

**🔴 handoff 的工具名从 agent 名生成**：`transfer_to_` + 名字里非 `[a-zA-Z0-9]` 全换成 `_`。中文名"退货专员"变成 `transfer_to_____`，第二个四字中文名专家会撞名，默认 `toolNameCollisionPolicy: 'warn'` 只警告不报错。agent 名用 ASCII，或 `handoff(agent, { toolNameOverride: 'transfer_to_returns' })`。

还有一条**代码编排**的路子（不靠 LLM 决策）：用结构化输出做分类再自己 `if/else` 派发、把上一个 agent 的输出喂给下一个、`Promise.all` 并行跑互不依赖的任务。**确定性要求高、要控成本和延迟时，别让 LLM 决定流程。**

完整讨论见官方 [Agent Orchestration](https://openai.github.io/openai-agents-js/guides/multi-agent/)，可跑样例在仓库 `examples/agent-patterns`。

**上生产** → `生产层-经验总结.md` §4：子 agent 的引用编号要请求级加锁分配、报告出口用真实数据机械改写格式（叮嘱模型没用）、甜点区是“广度×深度 > 单上下文”不是“任务多”。

## 决策二：对话历史怎么存——Session 的真实语义

`Session` 是多轮对话的记忆。主包直接导出现成的 `MemorySession`（`new MemorySession({ sessionId })`，内存态，官方标 demo/测试用），**按用户隔离就是一个 userId 一个实例**（`Map<userId, MemorySession>`），不用自己实现 `Session` 接口；上生产换 [Sessions 指南](https://openai.github.io/openai-agents-js/guides/sessions/) 里的持久化后端。

**先搞清 runner 到底在什么时机读写它**，否则会出现"历史丢了"或"存了两遍"：

| 时机 | runner 做什么 |
|---|---|
| **每次 run 之前** | 取出历史，跟本轮新输入合并，一起交给 agent |
| **非流式 run 结束后** | 一次 `session.addItems()`，**同时**写入用户输入和模型输出 |
| **流式 run** | 历史要等这一轮**完全结束**才完整（官方描述的实现是先写输入、后追加输出，但**实测从 `getItems()` 看不到这个中间态**——条目数从 2 直接跳到 4） |
| **从 `RunResult.state` 恢复**（审批等中断后） | 继续传**同一个** session；恢复的这轮直接入库，不再重新准备输入 |

### 别自己维护历史数组

给了 session 就别再手动往 input 里塞历史——runner 已经合并过了，手动再加就是重复。

**判断问句：这条消息，runner 会不会已经帮我存了？**

### 🟡 流式场景别在流没跑完时读历史

实测：非流式 run 结束后条目数 0 → 2（输入+输出各一条）；流式 run 在 `run()` 返回时、第一个事件到达时都还是旧值，**要等流消费完才变**。

所以做"实时同步聊天记录到数据库"这类需求时，**挂在流的事件上读 `getItems()` 会拿到不完整的历史**——要么等 `await stream.completed`，要么自己从事件流里攒。

### 做"撤销 / 清空聊天"用现成的 CRUD

```ts
await session.getItems();   // 取出全部历史（AgentInputItem[]）
await session.popItem();    // 弹掉最后一条 item（不是一轮）
```

**🟡 "撤回上一轮" ≠ `popItem()` 一次。** 一轮里夹着工具调用时是好几条（用户消息 + tool_call + tool_output + 回复 = 4 条），弹一条只会撤掉半截。要么从尾部循环 `popItem()` 直到弹掉最后一条 `role === 'user'` 的消息，要么每轮跑完记下本轮新增条数、撤回时按数弹。

自定义存储（数据库、Redis 等）要注意官方对**原子性和幂等性**的要求，见 [Sessions 指南](https://openai.github.io/openai-agents-js/guides/sessions/)。

**两个近期才加的能力**（2026-08，多数模型的训练数据里没有）：**session 历史事务**（并发写入的一致性保障）、**自定义 session 能拿到 run context**（存储层可以按用户/租户隔离）。要做多用户的聊天应用，这两个直接相关——**别按旧写法自己造锁**，先查官方 Sessions 页。

### 长对话会撑爆上下文

对话越长输入越大。长期运行的聊天应用**必须**考虑，别等报错才处理——六个开关的选法见**决策五**。

**上生产** → `生产层-经验总结.md` §2（展示历史和模型历史分两张表、预算裁剪三段式、被裁内容留取回工具）、§3（长期记忆两条轨，SDK 完全不管）。

## 决策三：状态放哪——两种 context 别搞混

| 类型 | 谁能看见 | 放什么 |
|---|---|---|
| **Local context**（`RunContext<T>`） | **只有你的代码**，模型看不见 | 用户 ID、logger、数据库连接、辅助函数 |
| **LLM-visible context** | 模型能看见 | 真的要让模型知道的信息（塞进 instructions 或输入） |

`RunContext<T>` 是你自己对象的包装，实际常用的是这几个字段：

- `runContext.context` —— **你的**应用状态（唯一属于你的字段）
- `runContext.usage` —— 本次运行的 token / 请求用量
- `runContext.toolInput` —— 当前跑在 `agent.asTool()` 里时的结构化输入
- `runContext.approveTool(...)` / `rejectTool(...)` —— 代码里改审批状态

两条硬规则：

1. **同一次运行里所有 agent / tool / hook 的 context 必须是同一个类型**
2. **🔴 别往 `runContext.context` 里放密钥** —— 如果你之后要序列化 `RunState`（做人工审批、断点续跑），运行时元数据会跟着一起存下来

## 决策四：危险操作要人点头——审批链路的完整走法

退款、删数据、发消息这类工具要人工批准。整条链路（源码 `runState.d.ts` / `result.d.ts` / `run.js` 核过）：

```ts
const refund = tool({ name: 'create_refund_ticket', parameters: z.object({...}),
  needsApproval: true,               // 也可以是 async (ctx, args) => boolean
  execute: async (args) => {...} });

// ① 正常跑；模型要调这个工具时 run 会停下，工具不执行
const result = await run(agent, input, { stream: true, session });
for await (const ev of result) { /* 会收到 run_item_stream_event / tool_approval_requested */ }
if (result.interruptions.length > 0) {
  pending.set(userId, result.state);  // ② 把 RunState 存起来（单进程存活对象即可；跨进程用 state.toString() / await RunState.fromString(agent, str)）
  // 告诉前端"等待批准"，把 item.rawItem.name / item.rawItem.arguments 带出去
}

// ③ 用户点了批准/拒绝
const state = pending.get(userId)!;
for (const item of state.getInterruptions()) {   // 或用你之前存的 result.interruptions
  approved ? state.approve(item) : state.reject(item);
}
const resumed = await run(agent, state, { stream: true, session });  // ④ 传 state 当 input、传同一个 session 续跑
```

四个实测确认的事实：

- **流里是先 `tool_called` 再 `tool_approval_requested`**，两个都发；UI 上把那条工具从 running 切到"等待批准"即可，别以为只来后一个。
- **恢复那轮不会重复入库**：`run.js` 里 `if (!isResumedState) prepareSessionHistoryTransactionsForRun(...)`，恢复态跳过；历史条目数从中断时的 N 变成 N+2（工具返回 + 回复），用户那句不会存两遍。
- **拒绝时工具真的没跑**：模型收到的工具输出是固定串 `"Tool execution was not approved."`，然后自己组织"没办成"的说法。
- **`RunToolApprovalItem` 上拿工具名和参数**：`item.rawItem.name` / `item.rawItem.callId` / `item.rawItem.arguments`（JSON 字符串），另有可选 `item.toolName` 兜底。

官方页 [human-in-the-loop](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/) 讲的就是这条链路；**用 WebFetch 抓那页只能拿到导航壳**，要原文抓仓库 raw：`https://raw.githubusercontent.com/openai/openai-agents-js/main/docs/src/content/docs/guides/human-in-the-loop.mdx`。

**上生产** → `生产层-经验总结.md` §5：会话级串行锁（同会话不能同时跑两个 run）、**断连≠取消**（必须有显式停止端点）、工具级停止用 return 不用抛、中止后的残局要写两处。

## 决策五：上下文怎么控——历史越滚越长时用哪个开关

对话越长，每轮送给模型的输入越大（工具返回、旧消息、图片 base64 全在里面）。SDK 给了六个开关，各管一段，**别自己在 input 数组上手撸裁剪**：

| 你想要 | 用什么 | 一句话 |
|---|---|---|
| 只送最近 K 轮 / 去掉旧的工具返回 | **`sessionInputCallback`**（run 选项或 RunConfig） | 模型调用前，拿到 `(historyItems, newItems)`，你返回最终要送的数组。**只在 input 是 `AgentInputItem[]` 时触发**，传字符串不触发 |
| 最后一步脱敏 / 丢旧消息 / 临时注入 instructions | **`callModelInputFilter`** | 收 `{ modelData: { input, instructions }, agent, context }`，返回同形状对象。官方称过滤会反映到入库；**实测（0.16.1）：改历史条目不写回、当轮新条目的过滤才入库**，且它连当轮工具循环的中间结果也会过——留保护窗（见 `agent-sdk.md` 差异附注） |
| 历史长了自动压缩成短的 | **`OpenAIResponsesCompactionSession`** 包住任意 Session | 每轮存完调 `responses.compact`；默认攒够 10 条非用户条目就压，`shouldTriggerCompaction: ({ compactionCandidateItems }) => …` 自定义；**不能包 `OpenAIConversationsSession`** |
| 历史干脆放 OpenAI 服务端 | **`conversationId`** 或 **`previousResponseId`**（run 选项，二选一） | 每轮只传新的一句；`previousResponseId` 用 `result.lastResponseId` 续。**只对 Responses API 有效** |
| 让 provider 自己压 | **`modelSettings.contextManagement: [{ type: 'compaction', compactThreshold }]`** | 服务端压缩，OpenAI Responses 专属 |
| 工具结果里的元数据（渲染提示、内部 ID）不进历史 | 函数工具的 **`customDataExtractor`** | 存到 `RunToolCallOutputItem.customData` 和 `RunState`，**不进 `history`、不回放给模型** |

再加三个相关的：`maxTurns`（默认 **10**，超了抛 `MaxTurnsExceededError`；长任务要调大或设 `null`）、`handoff(agent, { inputFilter: removeAllTools })`（转交时把工具调用记录裁掉，`removeAllTools` 从 `@openai/agents-core/extensions` 导）、图片进历史后每轮重发（见下节）。

**判断问句：状态放客户端（`result.history` / `session`）还是服务端（`conversationId` / `previousResponseId`）？一个对话只选一种**——混用会把上下文送两遍。四种策略的对照表在官方 [running-agents › Choose one memory strategy](https://openai.github.io/openai-agents-js/guides/running-agents/)。

最常用的两个：

```ts
// 只送最近 8 条历史 + 本轮新输入
await run(agent, newItems, { session,
  sessionInputCallback: (history, fresh) => [...history.slice(-8), ...fresh] });

// 自动压缩（关掉自动、手动压：shouldTriggerCompaction: () => false，之后 await session.runCompaction({ force: true })）
import { OpenAIResponsesCompactionSession, MemorySession } from '@openai/agents';
const session = new OpenAIResponsesCompactionSession({
  underlyingSession: new MemorySession({ sessionId: 'user:alice' }),
  shouldTriggerCompaction: ({ compactionCandidateItems }) => compactionCandidateItems.length >= 12,
});
```

**🔴 按条数裁历史别切在一轮中间**：`slice(-N)` 很容易把 `function_call` 切掉、把它的 `function_call_result` 留下，API 直接 400 `No tool call found for function call output`。SDK 的 `dropOrphanToolCalls` **只清"有调用没返回"**（源码 `runner/items.js` 只对 call 类型判配对，result 类型原样放行），反方向不管。裁完自己过一遍：窗口里 `function_call_result.callId` 找不到对应 `function_call` 的就丢；或者按"轮"（从 user 消息切）而不是按条数。另外 `sessionInputCallback` **在审批恢复的那次 run 上不触发**（恢复态跳过输入准备）。

**🟡 compaction 会拖慢流式收尾**：压缩是"清空底层 session 再重写"，SDK 要等它做完才 resolve `result.completed`——重的话最后一个 token 之后还要卡几秒。低延迟场景关自动、在两轮之间手动 `runCompaction()`。查决策过程开 `DEBUG=openai-agents:openai:compaction`。

**上生产** → `生产层-经验总结.md` §2：占位文写成取回工具的引导语、CJK 下 token 估算低估约 2.7 倍（换小窗口模型是必检项）、裁剪估算只全量算一次否则 O(n²)。**深拷贝坑的 TS 版实测结论见 `agent-sdk.md` 的差异附注**。

## 图片 / 文件输入

用户带图提问，input 不再是字符串，是一个 user 消息条目，`content` 数组里放文本 + 图：

```ts
const input = [{ role: 'user', content: [
  { type: 'input_text',  text: '这个订单怎么了？' },
  { type: 'input_image', image: 'data:image/png;base64,...' },   // 字段叫 image，不是 image_url；收 URL 字符串 / data URI / { id: fileId }
] }];
```

本地图片转 base64 data URI 最省事（`types/protocol.d.ts` 的 `InputImage` 定义）；文件同理用 `{ type: 'input_file', file: ... }`。图进了 session 之后**每一轮都会跟着历史重发**，图大或轮次多时要换 file id 或转成文字摘要。
