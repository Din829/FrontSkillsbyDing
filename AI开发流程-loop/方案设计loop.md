# 方案设计 loop

> 从 `入口.md` 问 1 路由进来：**还没有方案**的项目在这里把方案做出来。
> 流向：input 标准化 → 意图澄清（对话式）→（资料多则先知识构筑）→ 设计循环（对抗评审当裁判）→ 出厂 gate → 交给 `实现loop.md`。批量项目同此流向，设计循环的评审对象换成流水线定义本身。
> 本 loop 的契约：目标 = 产出能直接开工的方案；验证器 = 对抗评审 + 人工检查点；刹车 = 评审轮上限（默认 5，可按项目调）+ 兜圈检测；成果物 = 意图锚 + 方案 + 任务清单（或流水线三件套）+ 疑点清单（如有）。

## 何时用 / 何时不用

**适用**：有想法或资料、还没有方案；或有方案但任务没配验证命令（只走"带裁判的任务清单"一节补裁判）。

**不适用**：改造已有代码的单发小目标（迁移/清零/批量改写）——目标本身能机械判定，直接去 `实现loop.md`，给它设计一份方案是过度设计。判断问句：**这活的"什么算完成"现在就能写成验证命令吗？** 能，就不需要本 loop。

---

## 第一步：input 标准化

不变量：**任何资料进 loop 前，必须标准化成 agent 可靠消费的形态**（干净文本 + 可切片 + 可检索）。乱格式直接喂，精准无从谈起。

当前实现选择（快变层，可替换，核对于 2026-08-22）：本机 `docingest` 命令——任意格式（PDF/Office/HTML/图片/音视频/ZIP/URL）转干净 Markdown + chunks + 索引。没有它就手动转，标准不变。

---

## 第二步：意图澄清（对话式，不是 loop）

意图是定义"什么算对"的地方，只能来自人——所以这一步是对话，不进循环。已经带着意图锚进来的：核一遍"什么算对"的可翻译性（见模板下方硬要求），直接进第三步。

先摆正一件事：**九成情况下，人会先给大方向和背景**（哪怕就一两句："把这 600 个 COBOL 检查重写成 Java，行为要一致"）。所以 agent 的活不是"猜方向"，是**细化**——以人给的方向为纲，把一两句话变成可判定的意图锚。按 input 情形分档，但**人只出判断，不出劳动**：

| 情形 | agent 该干什么 | 人的工数 |
|---|---|---|
| **常态：人已给大方向/背景**（± 一堆资料） | 方向不用猜。从资料把细节做实——补边界、列假设、把"什么算对"写成可判定条目 → 起草意图锚 → 人确认纠偏 | 确认 + 纠偏 |
| 资料有、方向没说（少见） | 通读概貌提取方向假设，先一句话对方向（"是要做 X 吧？"），对上了再按常态细化 | 一句确认 + 纠偏 |
| 一句模糊想法、没资料 | 反问关键维度：给谁用 / 解决什么痛 / 什么算成功 / 不做什么 → 起草意图锚 → 人改/拍板 | 只答题，不写文档 |
| 连 idea 都要 agent 出 | 调研 + 给 1~3 个候选**带明确推荐**（不罗列让人挑） → 人选 | 只做选择题 |

规矩：**把人的工作从"写文档"压缩成"答问题、拍板"。** agent 可以生产 idea 候选，但"选哪个"必须人拍。
反例：把一份 20 项的需求问卷甩给用户填——这是把整理劳动推回给人。正确做法是 agent 先给出带推荐的草案，人在草案上说"对/不对/改这里"。
判断问句：**我是在让人做判断题，还是在让人做作文题？**

**减压规矩**（AI 时代人不愿判断、说明、决策——设计要顺应，不是对抗）：

- 能从资料、代码、常识里自己找到答案的，**不问人**——自己定，在意图锚里显式标"假设：…"。人拍板意图锚时顺带扫一眼假设列表即可，不必逐条被打断。
- 必须问的，**攒成一批一次问完**，每题带推荐答案（"我建议 A，因为…"），人回一句"都按推荐"就能过。
- 只有**拿捏不准、且答错会改变方向**的，才单独要人确认。

判断问句：**这个问题答错了，方案会报废吗？** 不会，就别打扰人。

### 意图锚模板（澄清的产物，<1 屏）

```markdown
# 意图锚：<项目名>
## 做什么
一两句话。
## 不做什么
边界，防范围漂移。划清边界比说做什么更重要。
## 什么算对
每条尽量写成可判定形式（见下方硬要求）。
## 约束
技术栈 / 期限 / 档位（瀑布或敏捷）/ 成果物要求（日式全套？）等。
```

**硬要求：「什么算对」的每一条，最终要能翻译成一个验证器**——测试、校验脚本、或至少一条明确的人工检查项。写不成可判定形式的不是标准，是愿望。
反例：「系统要稳定可靠」——判不了对错，等于没写。改成「压测 N 并发 30 分钟无 5xx」就能翻译成验证器了。
判断问句：**这条"算对"，将来拿什么说 no？**

这是贯穿全流程的金线：**意图 → 方案 → 验证器，一路可追溯。**

## 第三步：分流判断（两个问句，按序问）

1. **这批资料，agent 干活时临时翻，能保证精准吗？** 不能 → 先进"知识构筑 loop"（下节）再设计。资料就十几页 → 跳过，构筑是过度设计。
2. **这活是 N 个长得一样的小任务吗？** 是 → 方案按"批量流水线模式"（后节）产出；否 → 按"设计循环"产出单件方案。

## 知识构筑 loop（资料多到读不完时）

先花一次成本把资料"构筑"成可精准取用的知识结构（GraphRAG 同思路：先付索引成本，换后面每次取用又便宜又准；具体用图谱、索引还是一张 Markdown 地图，属快变层按项目挑）。

契约：目标 = 意图锚范围内的实体全部有状态（可判定：三角对账差集清零 + 抽检通过）；验证器 = 三角对账（机械）+ 抽检；刹车 = 预算上限（开跑前和人约定）+ 停滞检测（差集连续 2 轮不减即停）；成果物 = **地图**（知识条目）+ **疑点清单**。账本复用 `实现loop.md` 骨架，指纹换成"三角对账差集清单"。

### 条目三状态（证据对照用在知识库上）

| 状态 | 意思 | 规矩 |
|---|---|---|
| ✅ **有据** | 内容 + 出处（哪份文档哪节 / 代码哪几行） | 出处必须真实存在——可机械抽查 |
| 🔶 **推断** | 从证据合理推出，没直接写 | 必须列依据；用它的产物显式标"基于假设 X" |
| 【？】**疑点** | 不知道 | 进疑点清单，走生命周期 |

铁律：**没有出处的"知识"不许存在**——要么给出处，要么降级成推断或疑点。
判断问句：**这条知识被质疑时，我能一步跳到它的原文吗？**

### 疑点生命周期

标【？】时分不清是"资料里真没有（暗黙知，只在人脑子里）"还是"有但我没找到"——不许 AI 上来就下结论，靠流程分流：

```
① 标记：缺什么 / 哪个任务等它 / 查过哪里（方式+范围）/ 目前猜测+依据
② 补探：升级问人之前，换几种不同的探索方式重查——
   换关键词同义词（同一个东西常有几种叫法）/ 按实体反查（拿表名字段名搜）/
   翻附录图表 / 回标准化前的原文 grep（防转换丢信息）/ 换干净上下文 agent 重查
   （原来那个已被自己失败的查法带偏）。"有但没找到"的大部分死在这一步。
③ 升级问人：补探后还没有的才升级。措辞必须 claim-check 校准——
   不许说"资料里没有 X"，只许说"在已查范围内（列方式和范围）没有 X"。
   剩下的大概率是真暗黙知。
④ 回写：人的回答作为新条目写进地图，标"人答 + 日期 + 谁答的"。地图越用越全。
```

**阻断规矩**：关键疑点**只堵它挂着的那一件任务，不堵流水线**；非关键疑点作为显式假设写进那件的成果物。一句话：**疑点不许无声地进代码。**

疑点清单里升级问人的部分，就是日式项目的**質問票**——每条自带"我们查过哪里 + 我们的猜测"，客户经常只需回一句"你猜的对"（格式细节见 `成果物与证据.md`）。

### 三角对账（构筑 loop 的机械验证器）

补探治单个疑点，但更阴的是**压根没意识到某东西存在**——连【？】都没标。"不存在"没法直接验证，机械近似解是：**从多个独立来源各列一遍实体清单，互相对差集**。例：错误定义书的编号全集 / 老代码引用的表字段 / DDL 的表全集——三张清单一对，差集自动变成疑点。无声的空白被机械翻成有声的【？】。

### 容错原则

不追求 100% 准确，追求**零无声错误**：

- **显式的错**（标了疑点/推断，后来发现猜错）——正常成本，修条目就行。
- **无声的错**（标"有据"实为无据、说满了）——事故。抽检抓到一条，**修的是流水线不是那一条**（追问它为什么能溜过来）。

验证强度与**错误放大倍数**成正比：前部成果物（要件定義/地图）一条错污染下游全部，配三重**不同角度**的验证（三角对账 + 对抗评审 + 人抽检——三种角度互补；同一种检查跑三遍会漏同一个盲区）；末端单件错了就错一件，机械验证器兜底即可。阈值、抽检率是**可调参数**，真实项目打样时校准，不在本文写死。

## 设计循环（单件项目的主体）

设计跑不了 pytest，裁判换成对抗评审：

```
输入：意图锚 + 标准化资料（或地图）
循环：起草方案 → 对抗评审挑刺 → 修 → 直到评审无 🔴
出口：出厂 gate → 人工检查点（瀑布档必过；敏捷档可并入最终验收）
```

**对抗评审怎么跑**：评审者用干净上下文，只拿三样——方案草稿、意图锚、资料（或地图），不知道起草者的思路。挑四类刺：**遗漏**（意图锚的"什么算对"有没有哪条没被方案覆盖）、**矛盾**（方案内部 / 方案与资料打架）、**未验证的假设**（哪些断言没有出处也没标推断）、**过度设计**（为不存在的需求留的扩展位）。

**评审输出格式**（约定死，否则设计循环的判定标准悬空）：按四类刺分组列条目，每条给位置 + 问题 + 一句修法，并标严重度——🔴 不修不能出厂（违反意图锚 / 事实错误 / 关键遗漏）、🟡 该修可缓（表述不准 / 次要遗漏）、🟢 可不修。

**设计账本**：设计循环同样记账——复用 `实现loop.md` 的账本骨架，两处替换：「验证输出」→ 本轮评审发现清单原文；「错误指纹」→ 排序后的 🔴/🟡 条目列表。跨对话续跑、归档规则与实现 loop 相同；出厂 gate 的"🟡 处置有记录"就记在这里。

**刹车**：评审轮上限默认 5（可按项目调）；发现清单连续 2 轮相同 = 设计在兜圈子，停下来把分歧点原样汇报给人拍板，不要自己硬圆。

### 带裁判的任务清单（方案的强制产出）

**方案的最后一步是给每个实现任务配好裁判**——这是日式 V 字模型"设计阶段就定义测试"和 loop 工程"验证器先行"的同一个思想：2025 年用文档仪式实现它，现在用"任务自带验证命令"实现它。格式：

```markdown
| # | 任务（一句话目标） | 验证命令 | 判定标准 |
|---|---|---|---|
| 1 | 会员过期判定改为按日历日 | `pnpm test auth` | 失败数 = 0 |
| 2 | 建迁移校验脚本 verify_migration.py（任务 3 的前置） | 对样本数据真实跑通 | exit 0 且输出基线行数 |
| 3 | 迁移脚本处理 members 表 | `python verify_migration.py` | exit 0 且输出含 "rows matched" |
| 4 | 错误文案评审 | 对抗评审（对照文案规范） | 无 🔴 发现 |
```

裁判可以是三种验证器的任一种（机械优先），但**每行必须有**——无裁判的任务清单不许出厂，`实现loop.md` 会把它退回来。两条配套规则：

- **验证命令尚不存在的**（脚本没写、测试没建），必须显式排"建验证器"为前置任务行（如上例任务 2）——它自己的裁判 = 该命令能对当前代码真实跑出基线 + 过**红绿测试**（该红的输入真红、该绿的真绿，见 `入口.md` §二）。否则实现 loop 核对"命令还能跑"必挂，任务在方案↔实现之间乒乓。**测试数据的制作就是这类前置任务的典型形态**（agent 写规范 md、程序组装、schema/外键校验兜底——做法与格式见 `成果物与证据.md`）。
- **裁判为对抗评审的任务**（文档/文案类，如上例任务 4），实现侧按 `实现loop.md`"生成评估分离"节的方式跑评审，其余协议不变。

反例：任务写"优化性能"、验证命令写"人工确认"——两头都糊，实现 loop 进去就是漂移。

### 补裁判子流程（从入口问 1 或实现 loop 退回来的走这里）

对象：已有方案/任务清单，但任务没配验证命令，或原裁判失效。三步：

1. 逐任务把目标核成"一句话 + 什么算完成"——说不清的问人，不猜。
2. 配验证命令：自己找（翻 scripts / Makefile / CI 配置），报人一句确认；命令不存在的按上面规则排"建验证器"前置行。
3. 判定标准写清（exit 0 / 失败数 0 / 输出含标志）。

出口：**只补裁判的项目免整套出厂 gate**，只过两条——"每行有裁判"+ 人确认，补完直接回 `实现loop.md`。没有意图锚也不强制补全套：「什么算完成」已逐任务问清，意图降到了任务级。

## 批量流水线模式（N 个同构小任务）

判断问句：**这活是 N 个长得一样的小任务吗？**——是，方案的产物就不是 N 份设计，而是三样：**流水线定义（每件的处理配方）+ 地图 + 抽检策略**。

**件包（context pack）**：按地图给每件任务组装的小输入包——它的定义 + 相关 DDL 切片 + 相关文档段落 + 它的原代码。生成 agent **只吃件包，不搜全库**：精准靠地图建对一次，不靠每次临场发挥。

四步，每步有裁判：

1. **建地图**（一次性）：从原始材料机械提取每件的依赖清单（老代码里的引用是硬证据）。裁判 = 三角对账 + 抽样核对。这一步本身就是一个实现 loop。
2. **装件包**（机械）：按地图切片组装，脚本干，不靠 agent 记忆。
3. **打样**：先 3~5 件全流程跑通，人细看产物。发现的问题**修流水线不修单件**——改提取规则、改件包内容、改生成提示、加验证项。这是教训回写的批量形态：一条教训救后面几百件。
4. **批量 + 抽检**：每件过机械验证器（编译 + 单测 + 最好有黄金对照：同输入喂老系统和新代码，比结果）；**人工检查点从"每件看"变为"看流水线 + 抽检"**——抽检率就是档位旋钮在批量场景的形态（早期高、稳定后降；具体数值打样时定）。

**下游反哺**：实现 loop 写不通、测试矛盾、和老代码对不上 → 回写修地图。精度不是静态的，随批量递进收敛：打样抓大头、抽检抓漏网、下游摩擦抓残余。

流水线定义 + 抽检策略就是批量项目的"方案"——同样过设计循环的对抗评审和出厂 gate（gate 第 3 条的批量分支）。先后关系：**gate 在打样前过**，批准的是"可以开始打样的版本"；打样后的重大修订重过评审，小修记设计账本即可。

反例：600 件任务，agent 每件都去全库现找资料——又贵又不稳，第 400 件找错了没人知道。
判断问句：**第 N 件和第 1 件的差别，是"料不同"还是"做法不同"？** 只是料不同，就该上流水线。

## 出厂 gate（方案交付前，硬条件）

<阶段 gate>
- [ ] 意图锚存在，且"什么算对"每条可翻译成验证器
- [ ] 对抗评审通过（无 🔴 遗留；🟡 处置有记录）
- [ ] 单件：任务清单每行有裁判｜批量：流水线 + 地图 + 抽检策略三样齐
- [ ] 疑点清单处理完：答掉、或显式接受为假设（哪条假设影响哪个任务，写清）
- [ ] 方案里每个关键断言：有出处、或标了推断/假设——claim-check 过一遍
- [ ] 人工检查点：瀑布档人已拍板；敏捷档已明示"按敏捷档跳过，最终验收兜底"
</阶段 gate>

## 什么时候不要用本 loop

- 意图本身还在摇摆（人自己没想好要不要做）——先对话，方案做得再好也是给愿望配裁判。
- 单发可机械判定目标、小资料硬构筑——开头"何时不用"和第三步分流已各说过，不重复。

## 末尾速查

**标准化 input → 人只答题拍板出意图锚（每条"算对"可翻译成验证器）→ 资料多先构筑（有据/推断/疑点三状态，疑点走标记→补探→问人→回写，三角对账抓无声空白）→ 设计循环对抗评审挑四类刺 → 单件出"带裁判的任务清单"，批量出"流水线+地图+抽检"→ 出厂 gate：无裁判不出厂，疑点不无声进代码。**
