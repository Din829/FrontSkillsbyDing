# 实现 loop

> 对**单个可机械验证的目标**进行"改一点 → 跑验证 → 看结果"的冲刺循环，全绿后核验收尾，触发刹车则暂停。
> 从 `入口.md` 问 1 路由进来：方案清单逐任务在这里跑；目标、范围、验收已确认的独立小功能或单发改造也直接在这里定义，不要求已有代码。
> 批量同构项目（N 个长得一样的小任务）：每一件跑的都是本 loop，输入换成件包——流水线怎么搭见 `方案设计loop.md` 的批量模式节。

## 何时用 / 何时不用

**适用**：目标能用命令机械判定成败——修失败测试、类型错误清零、lint 清零、批量迁移、覆盖率达标、让某个验收脚本通过。（例外：方案清单里裁判为对抗评审的文档类任务也在本循环跑，验证命令换成评审，见"生成评估分离"节。）

**不适用**：设计、分析、调研、重构方向选择等无法机械判定"完成"的任务。**硬上 loop 是滥用**——循环的质量完全取决于验证器的质量，验证器是糊的，循环只会高效地走错路。回 `入口.md` 问 2 重新路由。

---

## 四条心法（贯穿全程）

### 1. 验证器就是天花板

loop 不可能比它的验证命令更聪明。验证弱（弱断言、覆盖不到关键路径），loop 会高效地收敛到一个**错误但全绿**的答案，且比人肉迭代更自信。所以 gate 里检查验证命令质量不是仪式，是命门。
判断问句：**这个验证命令，覆盖得到目标的关键路径吗？一个偷懒的实现能骗过它吗？**

### 2. 输出原文是事实，"通过了"是结论

每轮记命令、退出码和关键结果，**保留真实输出**：可直接贴进账本，也可引用该轮保存且不覆盖的原始日志，不必两处重复全文。只有“测试过了”四个字不够；PASS 是事实，功能对是结论，原文必须能沿记录找到。
判断问句：**这条结果能直接找到对应轮次的真实输出吗？**

### 3. 重试不能代替思考

连续没有有效进展就停，具体条件见“刹车”。错误指纹用于定位，不等于进展：同一个失败测试可能已修好部分路径，报错行号变了也可能什么都没修好。
判断问句：**这轮改善了什么，或用真实实验排除了哪种原因？证据在哪里？**

### 4. 变绿的方式比变绿本身重要

loop 里 agent 最危险的捷径全是"让验证器闭嘴"而不是"让代码正确"：改断言、删测试、加 skip、吞异常、给 fallback 值。这些动作让账面全绿、问题进暗处。Red Flags 表对此零容忍。
判断问句：**这轮变绿，是代码对了，还是验证器被弄哑了？**

## 启动协议（把契约四要素填成文）

契约四要素（目标 / 验证器 / 预算刹车 / 成果物）落到实现 loop，就是下面这些。按任务来源分 A/B；其中构建验证器的任务按 C 起步。

**A. 任务来自方案的"带裁判的任务清单"**（最常见）：目标、验证命令、判定标准都已配好。启动只做三件事：① 核对裁判仍然成立（命令还能跑、判定标准没过时）——核对不过 → 回 `方案设计loop.md` 补/修裁判，**不许自己顺手改判定标准**（改裁判是方案层的决定）；② 跑基线（见 gate）；③ 建账本——多任务连跑时，上一任务按 `成果物与证据.md` 记录完成或暂停状态后归档，再建新的；归档不等于完成。

**B. 单发目标**（直接从入口进来，没有方案）：对话式收集，**意图问人、技术细节自己拍板**：

1. **目标**——问用户一句话级别的目标 + 什么算完成。意图只有人知道，不清楚就停下来问，把困惑点具体说出来，不要猜。
2. **验证命令**——**自己找，不要先问人**：翻 package.json scripts / Makefile / CI 配置 / 项目 README。验收条件已明确且用户已授权选择技术命令时，记录选择依据即可，不重复确认；会改变“什么算对”时再问。项目缺测试就先按 C 构建验证器（含测试数据，规范见 `成果物与证据.md`），不把空跑或缺文件当业务验证。
3. **判定标准**——每条验证命令写清什么算过（exit 0 / 失败数为 0 / 输出含某标志）。模糊的判定标准等于没有。
4. **轮次上限**——默认 10，不问人。用户主动提了成本要求才调整。
5. **适用性判断**——目标不可机械验证时，**明确说不适合本 loop + 给替代路由**（回入口问 2），不把判断推给人。

收集齐后：在项目根建 `LOOP.md`（骨架见文末），填好头部，过 gate。单发或只补裁判的任务，头部同时写明范围、验收条件和档位，作为任务级意图锚；不补造完整方案，交付直接核销头部的验收条件。

**C. 构建验证器**（待建测试/检查脚本尚不存在或未校准）：四要素先写清，列出已知正确/错误样本及各自预期、可用的现有运行器和校准办法。实际运行一次初始检查；工具缺失或测试待建可以作为**建设基线**，但不算业务测试的红灯。此时允许进入构建，不要求待建工具已通过校准。完成前必须用正反例验证目标工具，并对当前业务产物跑出真实基线；两项都完成后，后续业务任务才能使用它。这样只豁免构建任务的启动时点，不降低验收要求。

业务产物尚未实现时，用已校准的验证器实际检查并记录“缺失/未实现”的失败基线即可，**不要求业务先通过**；确认失败来自待实现功能，不能把验证器本身无法启动或环境损坏当作这份业务基线。

## 进 loop 的 gate（硬条件，不可绕过）

<阶段 gate>
- [ ] 目标一句话写清，且有明确的"什么算完成"
- [ ] 验收条件已确认；验证命令和判定标准已记录。已授权的技术选择不重复问
- [ ] 验证命令**当前真实跑过一次**，基线状态已贴进 LOOP.md；C 类任务记录建设基线，区分缺文件/运行环境错误与业务失败
- [ ] 业务任务的验证器覆盖目标关键路径，新造的已过红绿校准；**C 类任务启动改查已知正反例、预期和现有运行器，工具校准在该任务出口完成**
- [ ] `LOOP.md` 已建好，头部填完
</阶段 gate>

任一不满足就停下来处理，不进循环。
反例："基线不用跑了，反正都是错"——没有基线就没法判断进展，第 3 轮时你分不清是修好了一半还是引入了新错。

## 循环体协议（每轮固定动作）

```
1. 读上一轮账本（错误指纹 + 下一轮计划）
2. 动手前 grep / Read 锚定本轮要改的代码段——不凭印象动手
3. 做最小增量修改（只为消掉当前错误，不顺手干别的）
4. 跑全部验证命令
5. 账本记关键结果与原始输出（直接贴或引用该轮日志；最终统计和失败清单须保留原文）
6. 对比错误指纹，并记录行为改善或新增诊断证据（没有就写无）
7. 判定：全绿 → 进收尾；有错 → 检查刹车条件 → 下一轮
```

**错误指纹**：失败用例名列表 / 错误码+文件位置列表，按固定方式排序后记录，只用于定位和比较。**有效进展**必须另附证据：目标行为改善，或真实实验缩小了根因范围。只改行号、换说法、重复旧证据、新增未经验证的猜测，都不算进展；失败名称不变也不抹掉已经证实的改善。

**跨对话接续**：读意图锚（单项任务用账本头部）+ 最后一轮，再核对工作目录、当前需求与代码/配置变化。账本交接时记录对应版本及未提交改动；没有版本管理时记相关文件或输入摘要。现场发生相关变化、或无法确认旧证据仍适用，就重跑相关验证并更新基线；未变化的部分不重复全套准备。记录帮助续跑，不能代替当前现场，也不能凭旧绿灯宣布本次完成。

---

## 刹车（两道，触发即停）

1. **轮次上限**：到达上限（默认 10）→ 停下汇报，给人三选项 + 推荐：继续 N 轮 / 换思路 / 人工接管。
2. **停滞检测**：连续 2 轮既没有目标行为改善，也没有缩小根因范围的新证据 → 停下汇报，说明“卡在哪、试了什么、怀疑根因、为什么没有进展”。指纹是否相同不能单独决定停/继续；有诊断进展也仍受总轮次上限约束。

刹车停下 ≠ 失败。带着具体困惑停下来，比烧完 10 轮交白卷有价值得多。

## 生成评估分离（高风险时上对抗评审）

默认 loop 是同一个 agent 自跑自验——靠验证命令和 Red Flags 防“放水”。相关实验观察到自评偏宽，但这不是所有模型、所有任务必然如此的定律；独立评估者同样可能偏宽，需要用已知正反例校准。

高风险场景升级为 `入口.md` §二的**对抗评审验证器**：一个干净上下文的评估者，只看本轮 diff + 验证输出 + 判定标准，不知道生成者的思路，独立判断"这轮到底过没过、有没有放水改测试"。生成者自评全绿、独立评估确认，才算数。

什么时候值得上：判定标准容易被钻空子（弱断言风险高）、改动碰了核心逻辑、或这轮明显有"想让验证器闭嘴"的诱惑。代价是多一次评估调用。**简单低风险的目标不必**——单 agent + Red Flags 够用，别为对齐而上结构。

## 红旗表（Red Flags）——防"让验证器闭嘴"的自检表

心里冒出下面任何一条——**停**。这是合理化，不是判断。

| 你心里想 | 真实情况 |
|---|---|
| "把这个断言改宽一点就过了" | 你在让验证器闭嘴，不是在修代码。改测试只有一种合法理由：测试本身错了——且必须在账本里显式记录"改了测试 + 为什么它原本就是错的" |
| "这个测试太边缘，skip 掉吧" | 同上。skip = 把红灯拔了说路通了 |
| "加个 try/except 就不报错了" | 吞异常是把问题推进暗处。fail loud 比账面绿更有价值 |
| "给这个字段配个 fallback 默认值就绿了" | fallback 掩盖的是配置或逻辑错误，循环结束后它还在 |
| "差不多了，先标完成" | 判定标准没全过就是没完成。诚实记账 |
| "报错位置变了，说明有进展" | 指纹只帮助定位。必须给出行为改善或新增诊断证据，再按刹车条件判断 |
| "顺手把旁边这个 lint 警告也修了" | 范围漂移。最小增量只为消当前错误，别的记下来收尾后说 |
| "只留总结，原文就不要了" | 可在账本简写并引用该轮原始日志；原文不可丢失或被后续运行覆盖 |
| "基线不用跑了，反正都是错" | 没有基线就没法判断进展，gate 不许过 |

## 收尾协议（全绿 ≠ 结束）

<阶段 gate>
- [ ] **独立对照一次**——全绿后换个方式核一遍，按场景选：亲眼读一段真实产物 / 换更狠的输入重跑 / 断言关键副作用真发生。防假绿灯：弱断言、mock 掩盖、单次孤证
- [ ] **diff 回看**——逐个改动问"这是目标要的吗"：顺手的风格调整、无关重构 revert；改过测试的，核对账本里有没有对应的"为什么测试原本是错的"记录
- [ ] **影响检查（按风险）**——判断词：改动会不会让别人读到的东西变了？改了共享逻辑/契约 → 搜下游引用核对；纯局部修复 → 不查，别上仪式
- [ ] LOOP.md 写完 `## 收尾核验` 段
</阶段 gate>

然后出报告（大白话，结论先行）：**课题**（目标是什么、起点多少错）/ **为什么这么改**（核心修法 + 关键转折轮）/ **预期效果**（基线 → 终态对比表）。报告措辞过 claim-check——实测的说实测，推断的说推断。

**出口按档位分流**（见 `入口.md` 问 3）：瀑布档 → 人工检查点，人放行才进下一任务；**已批准的批量任务例外**，按 `方案设计loop.md` 的批次/抽检约定放行，不逐件重复审批。敏捷档 → 记账后直接下一任务。C 类任务先完成工具校准与业务基线。交付按 `成果物与证据.md` 核销项目或任务级验收条件并归档证据。

## 教训回写（让循环越跑越难骗）

同一个错犯到**第二次**——同类 bug、同类误判、同一个被验证器漏掉的坑——不许只修不记：把教训写进项目 CLAUDE.md 或对应 skill（一两行，写"下次遇到 X 先查 Y"级别的具体话，不写感想）。

- 单件项目：教训进项目 CLAUDE.md。
- 批量流水线：教训**修流水线**（改件包规则 / 加验证项 / 改生成提示），一条教训救后面几百件。

判断问句：**这个坑，下一个干活的 agent（包括下周的我）还会掉进去吗？** 会，就必须回写。
反例：第 4 轮发现 SDK 的 X 默认值和文档不符，绕过去了没记——第 9 轮换个文件又撞一次，白烧两轮。

这是本体系唯一的自我进化机制，够用，不加更复杂的。

## 理论锚（这套循环不是拍脑袋；来源核对于 2026-08-22）

- **“写循环”的实践参考**：来源清单收录了 Boris Cherny 相关报道；这里只作为采用验证反馈闭环的设计参考，不据此承诺项目质量提升倍数。
- **验证器是命门**：没有验证的开环循环 = "自信地批量产出错误的机器"。
- **生成评估分离**：Anthropic《Harness design for long-running application development》（2026-03-24）报告了相关任务的自评偏宽及独立评估实践，也指出独立评估仍需校准。来源链接见 README；不外推为所有模型的必然规律。
- 完整来源清单见本文件夹 `README.md` 文末。具体数字会随产品迭代变化，需精确值时查原文。

## 末尾速查

**四要素成文才开跑，构建验证器按 C 起步；每轮最小增量 + 原文记账 + 进展证据，无有效进展两轮就停。续跑先核现场，全绿后独立对照 + diff 回看，二次踩坑必回写。变绿的方式比变绿本身重要。**
