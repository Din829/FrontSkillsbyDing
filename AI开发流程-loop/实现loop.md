# 实现 loop

> 对**单个可机械验证的目标**进行"改一点 → 跑验证 → 看结果"的冲刺循环，直到全绿才许停。
> 从 `入口.md` 问 1 路由进来：方案的任务清单逐个任务在这里跑；改代码类的单发目标（迁移 / 报错清零 / 批量改写）也直接在这里定义。
> 批量同构项目（N 个长得一样的小任务）：每一件跑的都是本 loop，输入换成件包——流水线怎么搭见 `方案设计loop.md` 的批量模式节。

## 何时用 / 何时不用

**适用**：目标能用命令机械判定成败——修失败测试、类型错误清零、lint 清零、批量迁移、覆盖率达标、让某个验收脚本通过。（例外：方案清单里裁判为对抗评审的文档类任务也在本循环跑，验证命令换成评审，见"生成评估分离"节。）

**不适用**：设计、分析、调研、重构方向选择等无法机械判定"完成"的任务。**硬上 loop 是滥用**——循环的质量完全取决于验证器的质量，验证器是糊的，循环只会高效地走错路。回 `入口.md` 问 2 重新路由。

## 四条心法（贯穿全程）

### 1. 验证器就是天花板

loop 不可能比它的验证命令更聪明。验证弱（弱断言、覆盖不到关键路径），loop 会高效地收敛到一个**错误但全绿**的答案，且比人肉迭代更自信。所以 gate 里检查验证命令质量不是仪式，是命门。
判断问句：**这个验证命令，覆盖得到目标的关键路径吗？一个偷懒的实现能骗过它吗？**

### 2. 输出原文是事实，"通过了"是结论

每轮验证结果必须**贴命令真实输出**进账本，不许用"测试过了"四个字代替。PASS 是事实，功能对是结论，中间差一层验证——原文在账本里，人和下一个 agent 都能复核；只有总结在账本里，谁也复核不了。
判断问句：**账本里贴的是命令输出，还是我的转述？**

### 3. 重试不能代替思考

连续撞同一堵墙就停。错误指纹连续 2 轮相同 = 当前思路有问题，继续重试是用算力代替思考。停下来汇报，让人拍板换路。
判断问句：**这轮和上轮，指纹变了吗？没变，我凭什么觉得再来一次会不同？**

### 4. 变绿的方式比变绿本身重要

loop 里 agent 最危险的捷径全是"让验证器闭嘴"而不是"让代码正确"：改断言、删测试、加 skip、吞异常、给 fallback 值。这些动作让账面全绿、问题进暗处。Red Flags 表对此零容忍。
判断问句：**这轮变绿，是代码对了，还是验证器被弄哑了？**

## 启动协议（把契约四要素填成文）

契约四要素（目标 / 验证器 / 预算刹车 / 成果物）落到实现 loop，就是下面这些。按任务来源分两种：

**A. 任务来自方案的"带裁判的任务清单"**（最常见）：目标、验证命令、判定标准都已配好。启动只做三件事：① 核对裁判仍然成立（命令还能跑、判定标准没过时）——核对不过 → 回 `方案设计loop.md` 补/修裁判，**不许自己顺手改判定标准**（改裁判是方案层的决定）；② 跑基线（见 gate）；③ 建账本——多任务连跑时，上一任务的账本先按 `成果物与证据.md` 的命名规则归档，再建新的。

**B. 单发目标**（直接从入口进来，没有方案）：对话式收集，**意图问人、技术细节自己拍板**：

1. **目标**——问用户一句话级别的目标 + 什么算完成。意图只有人知道，不清楚就停下来问，把困惑点具体说出来，不要猜。
2. **验证命令**——**自己找，不要先问人**：翻 package.json scripts / Makefile / CI 配置 / 项目 README，找到候选后报给人一句确认（"我打算用 `pnpm test` + `pnpm type-check` 做判定，OK？"）。实在没有才问；项目缺测试就明确建议先补测试再进 loop，不硬上——建验证器本身也是任务（含测试数据的制作，规范见 `成果物与证据.md`）。
3. **判定标准**——每条验证命令写清什么算过（exit 0 / 失败数为 0 / 输出含某标志）。模糊的判定标准等于没有。
4. **轮次上限**——默认 10，不问人。用户主动提了成本要求才调整。
5. **适用性判断**——目标不可机械验证时，**明确说不适合本 loop + 给替代路由**（回入口问 2），不把判断推给人。

收集齐后：在项目根建 `LOOP.md`（骨架见文末），填好头部，过 gate。

## 进 loop 的 gate（硬条件，不可绕过）

<阶段 gate>
- [ ] 目标一句话写清，且有明确的"什么算完成"
- [ ] 至少一条可执行验证命令 + 判定标准，已经用户确认（来源 A 的任务：方案拍板时已确认，不重复问）
- [ ] 验证命令**当前真实跑过一次**，基线状态已贴进 LOOP.md（知道起点有多少错，才能判断每轮有没有进展）。时点：**人确认命令之后再跑基线**——跑错命令的基线没意义
- [ ] 验证命令质量核过：覆盖得到目标关键路径；**新造的验证器必须过红绿测试**（该红的输入真红、该绿的真绿——恒真/恒假脚本当场现形）
- [ ] `LOOP.md` 已建好，头部填完
</阶段 gate>

任一不满足就停下来处理，不进循环。
反例："基线不用跑了，反正都是错"——没有基线就没法判断进展，第 3 轮时你分不清是修好了一半还是引入了新错。

## 循环体协议（每轮固定动作）

```
1. 读上一轮账本（错误指纹 + 下一轮计划）
2. 动手前 grep / Read 锚定本轮要改的代码段——不凭印象动手
3. 做最小增量修改（只为消掉当前错误，不顺手干别的）
4. 跑全部验证命令
5. 贴真实输出进账本（长输出可截关键段：最终统计 + 失败清单必须保留原文，不许改写）
6. 提取错误指纹，和上一轮对比
7. 判定：全绿 → 进收尾；有错 → 检查刹车条件 → 下一轮
```

**错误指纹**：失败用例名列表 / 错误码+文件位置列表，按固定方式排序后记录。作用是机械判断"这轮有没有真进展"——指纹变了是进展（哪怕错误数没少），指纹一字不变就是原地踏步。

**跨对话接续**：新对话或换 agent 时，读意图锚（如有）+ `LOOP.md` 头部 + 最后一轮即可继续，不需要历史对话。锚和账本就是全部状态——这也是"稳定不靠记性靠锚"的落地。

---

## 刹车（两道，触发即停）

1. **轮次上限**：到达上限（默认 10）→ 停下汇报，给人三选项 + 推荐：继续 N 轮 / 换思路 / 人工接管。
2. **停滞检测**：错误指纹**连续 2 轮完全相同** → 停下汇报。汇报里必须写"我卡在哪、试了什么、怀疑根因是什么"，不是只说"卡住了"。

刹车停下 ≠ 失败。带着具体困惑停下来，比烧完 10 轮交白卷有价值得多。

## 生成评估分离（高风险时上对抗评审）

默认 loop 是同一个 agent 自跑自验——靠 Red Flags 自律防"放水"。但 agent 评自己写的活必偏宽（这是被反复验证的规律，不是性格问题），自律有上限。

高风险场景升级为 `入口.md` §二的**对抗评审验证器**：一个干净上下文的评估者，只看本轮 diff + 验证输出 + 判定标准，不知道生成者的思路，独立判断"这轮到底过没过、有没有放水改测试"。生成者自评全绿、独立评估确认，才算数。

什么时候值得上：判定标准容易被钻空子（弱断言风险高）、改动碰了核心逻辑、或这轮明显有"想让验证器闭嘴"的诱惑。代价是多一次评估调用。**简单低风险的目标不必**——单 agent + Red Flags 够用，别为对齐而上结构。

## 红旗表（Red Flags）——防"让验证器闭嘴"的自检表

心里冒出下面任何一条——**停**。这是合理化，不是判断。

| 你心里想 | 真实情况 |
|---|---|
| "把这个断言改宽一点就过了" | 你在让验证器闭嘴，不是在修代码。改测试只有一种合法理由：测试本身错了——且必须在账本里显式记录"改了测试 + 为什么它原本就是错的" |
| "这个测试太边缘，skip 掉吧" | 同上。skip = 把红灯拔了说路通了 |
| "加个 try/except 就不报错了" | 吞异常是把问题推进暗处。fail loud 比账面绿更有价值 |
| "给这个字段配个 fallback 默认值就绿了" | fallback 掩盖的是配置或逻辑错误，循环结束后它还在 |
| "差不多了，先标完成" | 判定标准没全过就是没完成。诚实记账 |
| "这轮错误和上轮应该不一样"（没对指纹） | 对指纹是机械动作，不是感觉。指纹一样就触发刹车 |
| "顺手把旁边这个 lint 警告也修了" | 范围漂移。最小增量只为消当前错误，别的记下来收尾后说 |
| "输出太长，我总结一下贴" | 统计行和失败清单必须原文。总结无法复核 |
| "基线不用跑了，反正都是错" | 没有基线就没法判断进展，gate 不许过 |

## 收尾协议（全绿 ≠ 结束）

<阶段 gate>
- [ ] **独立对照一次**——全绿后换个方式核一遍，按场景选：亲眼读一段真实产物 / 换更狠的输入重跑 / 断言关键副作用真发生。防假绿灯：弱断言、mock 掩盖、单次孤证
- [ ] **diff 回看**——逐个改动问"这是目标要的吗"：顺手的风格调整、无关重构 revert；改过测试的，核对账本里有没有对应的"为什么测试原本是错的"记录
- [ ] **影响检查（按风险）**——判断词：改动会不会让别人读到的东西变了？改了共享逻辑/契约 → 搜下游引用核对；纯局部修复 → 不查，别上仪式
- [ ] LOOP.md 写完 `## 收尾核验` 段
</阶段 gate>

然后出报告（大白话，结论先行）：**课题**（目标是什么、起点多少错）/ **为什么这么改**（核心修法 + 关键转折轮）/ **预期效果**（基线 → 终态对比表）。报告措辞过 claim-check——实测的说实测，推断的说推断。

**出口按档位分流**（见 `入口.md` 问 3）：瀑布档 → 人工检查点，人放行才进下一任务；敏捷档 → 记账后直接下一任务。账本按 `成果物与证据.md` 归档——它就是試験エビデンス，任何档位不许删。

## 教训回写（让循环越跑越难骗）

同一个错犯到**第二次**——同类 bug、同类误判、同一个被验证器漏掉的坑——不许只修不记：把教训写进项目 CLAUDE.md 或对应 skill（一两行，写"下次遇到 X 先查 Y"级别的具体话，不写感想）。

- 单件项目：教训进项目 CLAUDE.md。
- 批量流水线：教训**修流水线**（改件包规则 / 加验证项 / 改生成提示），一条教训救后面几百件。

判断问句：**这个坑，下一个干活的 agent（包括下周的我）还会掉进去吗？** 会，就必须回写。
反例：第 4 轮发现 SDK 的 X 默认值和文档不符，绕过去了没记——第 9 轮换个文件又撞一次，白烧两轮。

这是本体系唯一的自我进化机制，够用，不加更复杂的。

## 账本骨架（启动时复制到项目根，命名 `LOOP.md`，agent 自行填写，人不需要碰）

两条铁律：**格式机械、内容自由**（heading 必须保留，保证 grep / 跨对话接续；段内自由发挥；不适用写 `N/A —— 因为...`）；**诚实记账**（输出贴原文不贴总结；指纹相同就承认相同；未全绿不能标完成）。

```markdown
# 目标循环账本

## 目标
一句话目标 + 什么算完成。

## 验证命令清单
| 命令 | 判定标准 |
|---|---|
| `pnpm test`（示例） | 失败数 = 0 |

## 配置
轮次上限：10　｜　停滞阈值：连续 2 轮指纹相同

## 状态
🚧 / ✅ / ⛔（刹车停止）　当前：Round N　最后更新：YYYY-MM-DD

## 基线（Round 0，进 gate 前必填）
验证命令的首次真实输出（关键段原文）：起点有多少错、错在哪。

---
## Round 1：标题（YYYY-MM-DD）
### 改了什么
文件级，最小增量。改过测试/断言的必须显式记录 + 为什么测试原本是错的。
### 验证输出
原文粘贴。长输出可截关键段——最终统计行 + 失败清单必须原文。
### 错误指纹
失败用例名 / 错误码+位置 的排序列表。和上一轮对比：变了 / 没变。
### 下一轮计划
一句话：下轮打算消哪个错、怎么消。全绿则写"进收尾"。

---
## Round 2：（继续追加）

---
## 收尾核验（全绿后必填）
- 独立对照：用什么方式核的 + 结果
- diff 回看：可疑改动有没有 / revert 了什么
- 影响检查：核了什么 / N/A —— 因为纯局部
- 基线 → 终态对比：起点 N 个错 → 0，共 M 轮
- 教训回写：写了什么进哪 / N/A —— 没有二次踩坑

## 刹车记录（如触发）
哪一轮触发、哪道刹车（上限/停滞）、卡在哪、试了什么、怀疑根因、给人的选项与推荐。
```

## 理论锚（这套循环不是拍脑袋；来源核对于 2026-08-22）

- **"写循环"是 Claude Code 之父的实践**：Boris Cherny 公开说现在的主要工作不是写 prompt 而是"写循环"；给 agent 一个能自查的验证反馈闭环，能把结果质量提升数倍。
- **验证器是命门**：没有验证的开环循环 = "自信地批量产出错误的机器"。
- **agent 自评偏宽**：Anthropic 的长任务 harness 框架把"生成"和"评估"拆成不同 agent，根本原因就是 agent 总会高估自己的产出。这是"生成评估分离"一节的依据。
- 完整来源清单见本文件夹 `README.md` 文末。具体数字会随产品迭代变化，需精确值时查原文。

## 末尾速查

**四要素成文才开跑，基线必贴，每轮最小增量 + 原文记账 + 指纹对比，撞墙两轮就停，全绿后独立对照 + diff 回看，二次踩坑必回写。变绿的方式比变绿本身重要。**
