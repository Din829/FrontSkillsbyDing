# 成果物与证据

> 从 `入口.md` 问 3（档位）和"其他时机路由"指过来。管三件事：**留什么**（成果物地图）、**怎么留**（归档约定）、**特殊件怎么做**（测试数据、質問票、交付报告）。
> 只适用于走了 loop 流程的项目——一两百行的小活没走流程，也就没有成果物义务。

**先分清两个词，全文件都建立在这个区分上：**

- **证据** = 复核用的原始记录：账本、验证输出原文、知识条目的出处、测试数据和结果。特点是"不看它就没法核对"。
- **文档** = 给人读的解释：设计书、报告、说明。特点是"丢了可以从证据重写"。

铁律：**敏捷省的是文档，不省证据。**
判断问句：**要砍掉一样东西之前问——砍的是文档还是证据？** 证据砍了，事后谁也无法证明"当时到底发生了什么"。

## 一、成果物地图（哪个环节产什么，日式项目怎么对号）

| 体系产物 | 产出环节 | 日式对应 | 性质 |
|---|---|---|---|
| 意图锚（含可判定的"什么算对"+ 假设列表） | 意图澄清 | 要件定義（受入基準込み） | 文档+证据 |
| 地图（知识条目，每条带出处）+ 疑点清单 | 知识构筑 loop（批量模式"建地图"步同） | 課題管理表 / 調査結果 | 证据 |
| 疑点清单里升级问人的部分 | 知识构筑 loop | 質問票 | 证据 |
| 方案文档 + 带裁判的任务清单 | 方案设计 loop | 基本設計 / 詳細設計 + WBS | 文档（清单行的裁判是证据） |
| 流水线定义 + 抽检策略（批量项目） | 方案设计 loop（批量模式） | 方式設計 + 検証計画 | 文档 |
| LOOP 账本（贴原文，含验证输出）| 实现 loop / 设计循环 / 知识构筑 | 試験エビデンス | 证据 |
| 测试数据三件套（规范 md + 数据文件 + 期望结果） | 实现 loop 的验证器建设 | 試験成果物 | 证据 |
| 交付报告（含验收对照表，claim-check 校准过措辞） | 收尾 | 完了報告（受入基準の消込付き） | 文档（对照表里的证据指针本身是证据） |

日企项目交付时，客户要的名目（要件定義書 / 基本設計書 / 試験エビデンス…）按此表对号；**表管"对应关系"，不管文件名**——客户要 Excel 的試験エビデンス就从账本转出、要試験成果物就从测试三件套转出，源头不变。

## 二、档位差异（瀑布全套 / 敏捷最小集）

| 产物 | 瀑布档 | 敏捷档 |
|---|---|---|
| 意图锚 | 必 | 必 |
| 方案文档 | 全套（基本/詳細設計分层） | 可薄至"任务清单 + 一页说明" |
| 带裁判的任务清单 | 必 | 必 |
| 账本（含验证输出原文） | 必，归档 | 必，归档 |
| 地图 + 疑点清单（如走了构筑） | 必 | 必（它们是证据） |
| 测试数据三件套 | 建了就必留、不删 | 建了就必留、不删 |
| 質問票 | 独立正式文档 | 疑点清单本身即可 |
| 交付报告 | 完了報告格式 | 几行的简短报告 |

规律一眼可见：**证据只随"有没有产生"变，不随档位省；形式可以随档位换**（質問票可以就是疑点清单本身）。两档的真正差别全部落在文档的厚薄上——这就是铁律的具体形态。

## 三、归档约定（含账本命名规则）

**三条不变量**（名字和位置都可按项目/客户要求换，这三条不能破）：

1. **证据不删**——任何档位、任何时点。
2. **集中可寻**——成果物聚在一处，不散落在代码目录里。
3. **能对上号**——从任何一份账本能看出它属于哪个任务、哪天跑的。

判断问句：**三个月后换台机器、换个 agent，凭这堆文件能复原全过程吗？** 不能，说明三条里破了至少一条。

**默认约定**（没有客户要求时照此，有要求按映射表换名）：

```
项目根/
├── 意图锚.md              ← 常驻项目根，不归档（它是锚，每个 loop 都要读）
├── LOOP.md                ← 当前正在跑的账本（任何 loop 运行时都用这个名，同一时刻只有一份在跑）
├── 方案.md（或 设计书/）   ← 带裁判的任务清单随方案放；批量项目的流水线定义+抽检策略同此位置
└── 成果物/
    ├── loops/             ← 账本归档，命名规则见下
    ├── 地图.md / 疑点清单.md   ← 构筑产物（活文档，常驻更新，标最后更新日）
    ├── 質問票.md
    ├── testdata/          ← 测试数据三件套
    └── 交付报告.md
```

**账本命名规则**（归档时改名）：
- 实现 loop：`LOOP-<任务#，没有任务号才用短名>-<收尾日 YYYYMMDD>.md`
- 非实现类 loop（设计循环、知识构筑）：`DESIGN-<项目或方案短名>-<收尾日 YYYYMMDD>.md`

**账本流转**：任务启动时项目根建 `LOOP.md` → 收尾核验写完 → **下一任务启动前**移入 `成果物/loops/` 按上述规则改名（与 `实现loop.md` 启动协议 A 的"上一任务账本先归档"是同一动作、同一时点）。

## 四、質問票格式（疑点升级问人的载体）

每条必带"查过哪里 + 我们的猜测"——这是降低对方回答成本的关键：客户经常只需回一句"你猜的对"。

编号沿用疑点清单的条目号。

```markdown
## Q-012：错误 E0453"特例代码 99"的含义
- 需要它干什么：E0453 的判定分支（任务 #453 被它阻塞）
- 查过哪里：错误定义书全文 / 业务文档"代码一览"章 / COBOL 注释
  （3 种方式，范围：已标准化的 42 份文档）
- 我们的猜测：疑似旧系统测试残留（依据：仅出现于 1998 年前的代码）。置信度低
- 请教：该代码的业务含义是？我们的猜测对吗？
- 状态：未回答 ／ 已回答（YYYY-MM-DD，回答者）→ 已回写地图
```

两条规矩：

- **没做过补探的疑点不许进質問票**（补探协议见 `方案设计loop.md` 疑点生命周期）——把"我懒得找"包装成"资料里没有"是对客户信任的透支。
- **回答必须回写地图**，标"人答 + 日期 + 谁答的"。問票只是通道，地图才是家。

判断问句：**这条質問，对方能在一分钟内答完吗？** 不能，说明我们自己的功课（查过哪里、猜测）还没做完。

## 五、测试数据（分工原则 + 规范 md 格式）

**分工原则**（跨项目不变）：

- **agent 决定**：这条 case 测什么、哪几个字段是关键、值是多少（**意图**）
- **程序负责**：其余字段从库/样本抽正常值、外键对齐、组装输出（**确定性**）

为什么这么切：agent 手写整行数据会幻觉字段名、外键断裂；程序又不知道这条 case 的灵魂字段是哪个。切在意图/确定性的边界上，与整个体系同构。
反例：让 agent 直接手写 30 列的 INSERT 语句——第 17 列的编码值多半是编的，而且查不出来。
判断问句：**这个字段的值，是这条 case 的"灵魂"还是"凑数的背景"？** 灵魂归 agent，背景归程序。

**规范 md 格式**（agent 的产出，组装程序的输入）：

```markdown
## case-001：会员过期后登录被拒
- 目的：验证过期判定分支
- 关键字段：member.expire_date = 昨日（制造过期）；member.status = active
- 其余字段：从库抽正常值
- 期望结果：登录返回 403
```

**组装怎么做**（快变层，核对于 2026-08-22）：不预制通用工具——agent 到项目现场写组装脚本更划算，脚本本身用机械验证器兜底（schema 校验、外键一致性检查跑一遍才算数）。参考实现（只读）：`副项目-和Dinreact区分/newaidrivenDev/tools/testdata/`——含外键自动解决、SQL 过滤、Excel 高亮输出，100+ 测试，2025 年产物，思路可抄、代码按需现代化。

**期望结果从哪来**：有老系统就从老系统来（黄金对照：同输入喂两边比结果，最强验证器）；没有就从意图锚的"什么算对"推，并标注推导依据。

**造好先跑一次红绿**：测试数据本身也是验证器，同样不能免检——设计来触发错误的 case 必须真让系统红，正常数据必须绿。两头有一头不对，先修数据再谈测代码。

三件套（规范 md + 数据文件 + 期望结果）= 日式試験成果物，归档进 `成果物/testdata/`。

## 六、交付：验收对照 + 交付报告（最后一道门）

**第一步：验收对照（金线的收口）。** 交付前把意图锚的"什么算对"**逐条核销**——每条指到兑现证据（哪个任务 / 哪份账本 / 哪轮验证输出）：

```markdown
| 什么算对（意图锚原文） | 兑现证据 | 状态 |
|---|---|---|
| 压测 30 分钟无 5xx | 成果物/loops/LOOP-7-20260823.md Round 4 输出 | ✅ |
| 过期会员登录被拒 | testdata/case-001 + LOOP-2 Round 2 | ✅ |
| 支持 CSV 导出 | ——（任务 #9 被疑点 Q-3 阻塞） | ❌ 未兑现，见下 |
```

核不上的条目只有两条路：**补做，或显式列为"未兑现 + 原因 + 人是否接受"**——不许静默缺席。意图从锚出发、最后回到锚验收，闭环。
判断问句：**意图锚里的每一条，现在都能指到它的证据吗？**

**第二步：交付报告。** 措辞过 claim-check（降级方案见 `入口.md` 其他时机路由），验收对照表附在报告里。格式遵循"课题 / 为什么这么改 / 预期效果"三段，大白话、结论先行。

规矩只有一条但硬：**报告里每个关键主张，读者能顺着它找到证据**——"全部通过"要能指到账本哪一轮，"性能提升"要能指到哪份输出。指不到的主张，降级措辞或删掉。
判断问句：**这句话被质疑时，我一步能点到哪份文件的哪一段？**

## 末尾速查

**证据（账本/输出原文/出处/测试数据）任何档位不省，文档按档位调厚薄。账本用完归档改名，意图锚常驻不动。質問票每条带"查过哪里+猜测"，回答必回写地图。测试数据 agent 管意图、程序管组装。交付前意图锚逐条核销——核不上的补做或显式认账。报告里指不到证据的主张不许说满。**
