## 一、为什么重新设计

旧设计包含固定阶段与细粒度关卡。哪些仍有必要，应按当前模型和任务实测，不能因模型进步就认定风险消失：

| 旧设计（2025~2026 上半年） | 当年补偿什么 | 现在 |
|---|---|---|
| newaidrivenDev：五阶段流水线 + Python gate + 2-5 分钟粒度任务 | 长任务与自评可靠性不足 | 按实际表现选择任务粒度，不把模型能力写成永久假设 |
| AI开发方法论-skills：四阶段 + PROGRESS 记账 heading + 阶段 gate | 靠流程约束维持精度 | 保留有效约束，去掉不影响验收的重复审批和整理劳动 |
| skill-目标循环 | （它不老，就是站位反了） | loop 从"阶段三里的冲刺模式"升为**默认工作单元** |

这正是《演进式解耦架构》说的病：把短期假设（模型弱）焊死在了核心。新设计把方法论自己也按"变化速度"分层，慢变的做骨架，快变的可替换。

## 二、全景：一句话 + 一张图

**骨架只定义"一个 loop 长什么样"（契约），不定义"有哪些阶段"（流水线）。**

```
人的 input（任意穷富程度）
   │
   ▼
┌─ 入口路由（三问）────────────────────────────┐
│ ① 你手里有什么？                              │
│    只有想法/资料 ──→ 意图澄清（对话式，人答题拍板）  │
│    意图仍需展开设计 ──→ 方案设计 loop           │
│      （资料多到翻不准 → 先知识构筑 §六.1；       │
│        N 个同构小任务 → 批量流水线 §六.2）        │
│    有方案       ──→ 实现 loop（逐任务）         │
│    已明确的单项实现（可含新功能）→ 直接定义实现 loop │
│ ② 这活能机械验证吗？ 能建验证器就先建；          │
│    建不出、也没意图锚可对照 → 别硬上 loop，对话推进 │
│ ③ 档位？ 瀑布（成果物全+人审批） / 敏捷（轻记账）   │
└──────────────────────────────────────────┘
   │
   ▼
每个环节 = 一个 loop 实例，全部长同一个样子（契约）：
   目标 + 验证器 + 预算/刹车 + 成果物
   │
   ▼
交付：验收对照（意图锚逐条核销）→ claim-check 校准措辞 → 成果物归档（=日式エビデンス）
```

扩展性来源：将来出新玩法（新 loop 模式、更强模型、新产品功能），**加一个 loop 文件就行，骨架不动**。loop 类型是插件，不是阶段。

## 三、骨架的全部：loop 契约 + 三种验证器

### loop 契约（开跑前必须写清的四样，写不清不许进）

| 要素 | 是什么 | 少了会怎样 |
|---|---|---|
| **目标** | 一句话 + 什么算完成 | agent 漂移，永远"差不多了" |
| **验证器** | 能说 no 的东西（下表三种之一） | 循环变成"自信地批量产错的机器" |
| **预算/刹车** | 轮次上限 + 基于有效进展的停滞检测（按 `实现loop.md`“刹车”，不只看指纹） | 用重试代替思考、烧钱 |
| **成果物** | 这个 loop 结束留下什么证据 | 人无法复核、下次无法接续 |

### 三种验证器（解决"设计类工作没法机械验证"的关键）

| 形态 | 用在哪 | 强度 |
|---|---|---|
| **机械验证器**：测试 / 类型检查 / 校验脚本 | 实现、迁移、测试数据 | 最强，首选 |
| **对抗评审验证器**：干净上下文的评审者专职挑刺 | 方案、文档、规格类产物 | 中，防自评偏宽 |
| **人工检查点**：人拍板 | 意图、方向、验收 | 最贵，只用在判断不可替代处 |

规矩：**能机械就机械，机械不了上对抗评审，人只出现在"定义什么算对"的地方。**

新造验证器的自证：业务使用前须有真实基线与红绿校准，正确/错误产物都能判对，还要检查关键路径覆盖。**构建任务按 `实现loop.md` 启动 C**，先记录已知样本、预期、运行器和建设基线，目标工具的校准在出口完成；不要求未写出的工具先合格。业务负例被正确处理应测试通过。措辞校准归证据对照。

gate 的定位：gate = 挂在每个 loop 上的验证器，**不是阶段之间的审批仪式**。

判断问句：这个 gate 拦下的是"错误"还是"没走流程"？拦错误的留，拦流程的删。

## 四、稳定 + 精准的七个机制

灵活和稳定不打架的原因：**灵活在路由层**（进哪个 loop、成果物多厚），**稳定在 loop 内部**（契约固定）。两层各管各的。

**稳（不跑偏、可恢复）：**

1. **读锚并核现场**——项目意图锚（单项任务可用账本头部）+ 最后一轮帮助续跑，但旧记录不代替当前代码/需求。恢复前核对相关变化，必要时重跑验证更新基线。
2. **最小增量 + 每轮过验证**——错误指纹用于定位，另用行为改善或真实诊断实验的证据判断进展；行号变化不算进展，失败测试同名也不等于停滞。
3. **刹车**——连续 2 轮无有效进展或达到轮次上限就汇报，细则以 `实现loop.md` 为准。

**准（做的是对的事）：**

4. **验证器先行**——业务实现前验收条件已确认、裁判已校准、基线已跑过；构建验证器按启动 C 的时点要求。
5. **红旗表**——防"让裁判闭嘴"类捷径：改断言、skip 测试、吞异常、fallback 值。（原目标循环 skill 那张表全保留）
6. **生成评估分离**（高风险时）——用干净上下文评审降低自评偏宽风险，独立评审也要校准，不视为天然可靠。
7. **交付校准**——汇报走 claim-check：PASS 是事实、"功能对"是结论，措辞不越过证据。人在循环上方，只看得见汇报，这是人机信任的最后一道门。交付前先做**验收对照**：意图锚"什么算对"逐条核销到证据，核不上的补做或显式认账——金线的收口（2026-08-23 补充，对应旧体系 Phase 4 Verify 的追溯职能）。

## 五、Input 处理（含"只有 idea"的情况）

**不变量只有一条：任何 input 进 loop 前必须标准化成 agent 可靠消费的形态。**
（docingest 是当前的实现选择，属快变层，可替换。）

常态前提（2026-08-22 补充）：九成情况下人会先给大方向/背景——**agent 不猜方向，只负责把人的一两句话细化成可判定的意图锚**；"从资料反推方向"只是方向缺失时的兜底。按穷富分档：

| 你手里有 | 流程 | 人的工数 |
|---|---|---|
| 大方向/背景（人给的）± 一堆乱文件 | docingest 标准化 → agent 以人给方向为纲，从资料做实细节（边界/假设/可判定的"算对"） → 人确认 | 确认 + 纠偏 |
| 只有模糊想法（"我想做个 X"） | **意图澄清协议**：agent 反问关键维度（给谁用 / 解决什么痛 / 什么算成功 / 不做什么）→ agent 起草意图锚 → 人改/拍板 | 只答题，不写文档 |
| 连 idea 都想让 agent 出 | agent 调研 + 给 1~3 个候选带推荐 → 人选 | 只做选择题 |

核心原则：**把人的工作从"写文档"压缩成"答问题、拍板"。** agent 可以生产 idea 候选，但"选哪个"必须人拍——意图是定义"对"的地方，模型再强这条也不变。

减压补充（2026-08-22）：问人也要省着问——能自己找到答案的自己定（显式标"假设"，人拍板意图锚时一并扫）；必须问的攒批、带推荐；只有拿捏不准且答错会改变方向的才单独确认。

### 意图锚（澄清的产物，<1 屏）

四段：做什么 / 不做什么 / 什么算对 / 约束。

硬要求：**"什么算对"的每一条，最终要能翻译成一个验证器**（测试、脚本、或至少一条人工检查项）。写不成可判定形式的不是标准，是愿望。

这是贯穿全流程的金线：**意图 → 方案 → 验证器，一路可追溯。**

## 六、方案设计 loop（没有方案、只有 input 时）

设计跑不了 pytest，但可以是 loop——裁判换成对抗评审：

```
输入：意图锚 + 标准化资料
循环：起草方案 → 对抗评审 subagent 挑刺
      （对照意图锚+资料：遗漏？矛盾？未验证的假设？过度设计？）
      → 修 → 直到评审过
出口：人拍板（瀑布档必过；敏捷档可选）
```

评审轮上限默认 5（可调）；连续 2 轮无有效进展则暂停，按 `方案设计loop.md` 的设计刹车判定，不仅比较发现清单措辞。评审输出按四类刺分组、每条标 🔴（不修不能出厂）/🟡（该修可缓）/🟢（可不修）。

**产物的关键要求：方案必须输出"带裁判的任务清单"**——每个任务自带一句话目标 + 验证命令 + 判定标准。设计的最后一步是给每个实现任务配好裁判，实现 loop 拿到就能开跑。

> 日式 V 字模型的精髓（设计阶段就定义测试）和 loop 工程的"验证器先行"是同一个思想。2025 年用文档仪式实现它，现在用"任务自带验证命令"实现它。

UX/前端接线（2026-08-24 补充）：任务含用户界面时——**定调（给谁用/气质）属意图级并进意图锚人拍板；UI 产物的对抗评审判定标准取自 `前端skills/`（119 条 UX 规则/自检门）；落码用其检查脚本当机械验证器**——前端skills 三层内容恰好对应三种验证器，零改造挂进契约。无界面系统此分支不存在（判断问句：有人要看、要操作的界面吗？）。前端skills 保持自包含红线，只许 loop 单向指向它。另：方案中外部依赖/业界能力的断言必须检索权威源标日期，凭记忆 = 未验证。

### 六.1 资料多到读不完：知识构筑 loop（2026-08-22 补充，来自真实项目经验）

触发判断问句：**这批资料，agent 干活时临时翻，能保证精准吗？**——不能就先花一次成本构筑（GraphRAG 同思路：先付索引成本，换后面每次取用又便宜又准；具体用图谱还是索引还是一张 Markdown 地图，属快变层按项目挑）。资料就十几页则直接读，构筑是过度设计。

产物两样：**地图**（知识条目）+ **疑点清单**。

**条目三状态**（证据对照用在知识库上）：

| 状态 | 意思 | 规矩 |
|---|---|---|
| ✅ 有据 | 内容 + 出处（哪份文档哪节 / 代码哪几行） | 出处必须真实存在，可机械抽查 |
| 🔶 推断 | 从证据合理推出，没直接写 | 必须列依据；用它的产物显式标"基于假设 X" |
| 【？】疑点 | 不知道 | 进疑点清单，走生命周期 |

铁律：**没有出处的"知识"不许存在**——要么给出处，要么降级成推断或疑点。

**疑点生命周期**（"真暗黙知"和"有但没找到"分不清，靠流程分流）：

```
① 标记（缺什么/哪个任务等它/查过哪里+范围/目前猜测+依据）
→ ② 补探（换关键词同义词 / 按实体反查 / 翻附录图表 / 回标准化前原文 grep / 换干净上下文 agent 重查）
→ ③ 升级问人（措辞必须 claim-check 校准："在已查范围内（列方式和范围）没有 X"）
→ ④ 回写（人答 + 日期 + 谁答的，入库）
```

阻断规矩：关键疑点**只堵它挂着的那一件任务，不堵流水线**；非关键疑点作为显式假设写进那件的成果物。一句话：**疑点不许无声地进代码。**

**三角对账**：先统一范围、实体类型和标识，再比同类清单（如代码引用表名与 DDL 定义表名）；不同类通过关系表查引用覆盖，不拿错误编号与表名直接求差集。出口是未解释差异为零、抽检通过；合法差异保留解释，关键未解项阻断关联任务，不把任务记为完成。操作细则见 `方案设计loop.md`。

散落逻辑的线索链（2026-08-23 补充，来自真实项目经验）：逻辑要跨文件拼合时，地图条目加记**关系**（引用谁/被谁引用/线索跳转路径），拼合结果标推断、线索链为依据；关系多到 Markdown 记不动就升级图谱型地图。

**容错原则**：不追求 100% 准确，追求**零无声错误**。显式的错（标了疑点/推断后来发现猜错）是正常成本；无声的错（标"有据"实为无据）是事故——抽检抓到一条，修的是流水线不是那一条。验证强度与错误放大倍数成正比：前部成果物（要件定義/地图）配三重不同角度验证（三角对账 + 对抗评审 + 人抽检），末端单件靠机械验证器兜底。阈值、抽检率定为**可调参数**，真实项目打样时校准。

### 六.2 N 个同构小任务：批量流水线模式（2026-08-22 补充，来自真实项目经验）

判断问句：**这活是 N 个长得一样的小任务吗？**——是，方案的产物就不是 N 份设计，而是：**流水线定义（每件的处理配方）+ 地图 + 抽检策略**。

**件包（context pack）**：按地图给每件任务组装的小输入包（它的定义 + 相关 DDL 切片 + 相关文档段落 + 它的原代码）。生成 agent **只吃件包，不搜全库**——精准靠地图建对一次，不靠每次临场发挥。

四步，每步有裁判：

1. **建地图**（一次性）：从原始材料机械提取每件的依赖清单；裁判 = 三角对账（见 §六.1）。
2. **装件包**（机械）：按地图切片组装。
3. **打样**：先 3~5 件全流程跑通，人细看；发现的问题**修流水线不修单件**（教训回写的批量形态——一条教训救后面几百件）。
4. **批量 + 抽检**：每件过机械验证器（编译+单测+最好有黄金对照）；已批准的范围按批次/抽检约定放行，瀑布档也不逐件重复审批。抽检失败暂停受影响批次，重大范围或判定标准变化重新拍板。具体优先规则见 `方案设计loop.md`。

下游反哺：实现 loop 写不通、测试矛盾、和老代码对不上 → 回写修地图。精度不是静态的，随批量递进收敛：打样抓大头、抽检抓漏网、下游摩擦抓残余。

## 七、实现 loop

原 skill-目标循环 升级站位，保留核心动作，并按反例修正判断条件：

```
逐任务：读账本 → 锚定代码 → 最小修改 → 跑验证 → 保留原文或日志引用
        → 指纹对比 + 进展证据 → 判定
刹车：轮次上限 / 连续 2 轮无有效进展（按实现 loop 定义）
收尾：独立对照防假绿灯 → diff 回看 → 影响检查 → 账本收口
```

保留的核心资产：四条心法（验证器就是天花板 / 输出原文是事实 / 重试不能代替思考 / 变绿的方式比变绿重要）、错误指纹、红旗表、收尾协议、可选的独立评估 subagent。

新增一条——**教训回写**：同一个错犯第二次，把教训写进项目 CLAUDE.md 或 skill，让循环越跑越难骗。这是体系自我进化的唯一机制，够用，不加更复杂的。

## 八、测试数据

**分工原则（2025 年验证过的，原封带走）：**

- agent 决定：这条 case 测什么、哪几个字段是关键、值是多少（**意图**）
- 程序负责：其余字段从库抽正常值、FK 对齐、组装输出（**确定性**）

为什么这么分：agent 手写整行数据会幻觉字段、FK 断裂；程序又不知道这条 case 的灵魂字段是哪个。切在意图/确定性的边界上，与整个体系同构。

**规范 md 格式**（agent 的产出，机器的输入）：

```markdown
## case-001：会员过期后登录被拒
- 目的：验证过期判定分支
- 关键字段：member.expire_date = 昨日（制造过期）；member.status = active
- 其余字段：从库抽正常值
- 期望结果：登录返回 403
```

**实现方式的时代变化**：2025 年要预制通用 generator（newaidrivenDev `tools/testdata/`，含 FK 自动解决、Excel 高亮输出，100+ 测试）；现在模型强了，**agent 到项目现场写组装脚本更划算**，脚本本身用机械验证器兜底（schema 校验、FK 一致性检查）。

新体系只带走：规范 md 格式约定 + 分工原则 + 参考实现指针（`副项目-和Dinreact区分/newaidrivenDev/tools/testdata/`，只读）。**工具不预制，从真实项目里长。**

产出三件套「规范 md + 数据文件 + 期望结果」= 日式試験成果物。

期望结果从哪来（2026-08-22 补充）：有老系统就从老系统来（黄金对照，最强验证器）；没有就从意图锚的"什么算对"推，并标注推导依据。

## 九、日式与档位

成果物映射（日企项目直接对号入座）：

| 体系产物 | 日式对应 |
|---|---|
| 意图锚（含可判定的"什么算对"+ 假设列表） | 要件定義（受入基準込み） |
| 地图 + 疑点清单 | 課題管理表 / 調査結果 |
| 方案文档 + 带裁判的任务清单 | 基本設計 / 詳細設計 + WBS |
| 流水线定义 + 抽检策略（批量项目） | 方式設計 + 検証計画 |
| 任务清单验证命令列 + 测试数据规范 md | 試験設計書 / 試験仕様書 |
| LOOP 账本 + 测试原文（内嵌或引用日志） | 試験エビデンス |
| 测试数据三件套 | 試験成果物 |
| 疑点清单（升级问人的部分，自带"查过哪里+我们的猜测"） | 質問票 |
| 交付报告（含验收对照表，claim-check 过的） | 完了報告（受入基準の消込付き） |

档位就一个旋钮：

- **瀑布档**：每环节人工检查点必过、成果物全套（日企项目）；已批准批量任务按批次/抽检约定放行
- **敏捷档**：人工检查点只留"意图"和"验收"两处、文档从简

铁律：**敏捷省的是文档，不省证据**——账本和验证原文任何档位都必须留。

单项任务（含已明确的新功能）可用账本头部的目标、范围、验收条件和档位代替独立意图锚及单行任务清单，不补造完整方案。原始日志可引用而不重复全文。归档按 `成果物与证据.md` 区分类型和序号；已完成或明确受阻都可归档，但保留真实状态及已用预算，旧证据和链接保持可用。

## 十、什么时候不要用这套

- 一两百行的一次性脚本、临时调试、一次性数据处理——直接干，上流程是过度设计（判据是"一次性"；常驻使用、连真实数据的小工具走最薄敏捷档，2026-08-22 盲测补充）。
- 目标无法机械验证、也没有可对照的意图锚的纯探索——先对话把意图聊出来，别硬套 loop。
- 长命核心代码的大规模自主生成要警惕（Ronacher 边界）：loop 最擅长改造已有代码和产物可验证的活；防御性垃圾堆积、人失去代码理解，是 loop 的两大慢性病，靠红旗表 + 人工检查点压制，但不要指望根治。
